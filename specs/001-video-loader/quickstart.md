# Quickstart: Validating the Video Loader

This is a manual/automated validation guide for the Video Loader feature once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/video_loader_contract.md](./contracts/video_loader_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`).
- A small valid sample MP4 file and a small valid sample MKV file (a few seconds long is sufficient — duration doesn't need to be 3-4 hours to validate correctness).
- A deliberately corrupted file (e.g., a truncated copy of a valid video), a zero-byte file, and a file with an unsupported extension (e.g., `.avi`) for the rejection-path scenarios.
- A file held open exclusively by another process, to validate the `FILE_LOCKED_OR_INACCESSIBLE` path (Acceptance Scenario 5).
- The deterministic multi-hour synthetic fixture generated by `tests/fixtures/video_loader/generate_fixtures.py` (see tasks.md T007), for the SC-001/SC-005 performance check in Scenario 3 below. A real 3-4 hour match recording is a good additional check before final sign-off, but the synthetic fixture is what makes this scenario repeatable in CI.
- No network connection required or expected — the loader must not attempt any (SC-004).

## Scenario 1 — Load a valid video (User Story 1)

1. Run the loader against the sample MP4: `load_video("<path-to-sample.mp4>")`.
2. Expected: `LoadResult.status == SUCCESS`, with `source.duration_seconds`, `source.resolution`, `source.frame_rate`, `source.frame_count`, `source.codec`, and `source.file_hash` all populated and matching the sample file's known properties.
3. Repeat with the sample MKV file. Expected: same outcome, `container_format == MKV`.
4. Run the loader against the same MP4 fixture a second time. Expected: `source.file_hash` is identical across both runs (FR-014). Run it against the MKV fixture and confirm its `file_hash` differs from the MP4's.

## Scenario 2 — Reject invalid inputs (User Story 2)

1. Run the loader against a nonexistent path. Expected: `status == FAILURE`, `failure_reason == FILE_NOT_FOUND`.
2. Run the loader against the `.avi` (unsupported format) file. Expected: `status == FAILURE`, `failure_reason == UNSUPPORTED_FORMAT`.
3. Run the loader against the corrupted/truncated file and the zero-byte file. Expected: `status == FAILURE`, `failure_reason == CORRUPTED_OR_UNDECODABLE` for both.
4. Run the loader against the file held open by another process (from Prerequisites). Expected: `status == FAILURE`, `failure_reason == FILE_LOCKED_OR_INACCESSIBLE` — distinct from the `CORRUPTED_OR_UNDECODABLE` results in step 3.
5. Confirm each attempt in steps 1-4 produced a log entry with enough detail to identify the cause (FR-007), and that no scene detection / OCR / event detection code path was invoked.

## Scenario 3 — Offline, CPU-only, performance budget (User Story 3, SC-001, SC-004, SC-005)

1. Disconnect the test machine from the network (or run in a network-isolated sandbox).
2. Run the loader against the valid sample MP4/MKV files from Scenario 1. Expected: identical success results as Scenario 1 — no behavior differs without network access.
3. On target-class hardware (or a comparable CPU-only machine), run the loader against the deterministic multi-hour synthetic fixture (from Prerequisites). Expected: `LoadResult` returned within 10 seconds (SC-001), and process memory attributable to the loader stays at or under ~200MB (SC-005). As an additional check before final sign-off, repeat against a real 3-4 hour match recording if one is available.

## Scenario 4 — Diagnostics emission (FR-013, SC-006)

1. Run the loader against any fixture from Scenarios 1 or 2 (success or failure case).
2. Confirm exactly one structured `ExecutionDiagnostics` log record is emitted per call, containing `module_name`, `start_time`, `end_time`, `duration_seconds`, `peak_memory_mb`, `input_summary`, `output_summary` (or `failure_reason`), and `warnings` — per [data-model.md](./data-model.md).
3. Confirm the record is valid, parseable structured output (e.g., a single JSON object per line), not free-form text.

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

## Results (2026-07-27, automated equivalent via pytest — see tasks.md T028)

Run on this development machine (not yet target-class hardware) via the automated test suite in `tests/{unit,contract,integration,benchmark}/`, which exercises the same fixtures and assertions described above.

- **Scenario 1** (valid video load): PASS — `tests/integration/test_video_loader_e2e.py::test_load_valid_mp4_succeeds_with_correct_metadata` and `test_load_valid_mkv_succeeds_with_correct_metadata`; hash stability/distinctness confirmed by `test_file_hash_is_stable_across_repeated_loads` and `test_file_hash_differs_between_distinct_files`.
- **Scenario 2** (reject invalid inputs): PASS — all 5 sub-cases (missing file, unsupported format, corrupted, zero-byte, locked) pass as distinct `failure_reason` values; see `tests/integration/test_video_loader_e2e.py`.
- **Scenario 3** (offline, performance budget): PASS on the synthetic multi-hour fixture — `tests/benchmark/test_video_loader_performance.py` measured well under the 10s/200MB budget (the fixture's tiny encoded size means this doesn't yet stress I/O the way a real multi-GB broadcast file would; re-run against a real 3-4 hour recording before final production sign-off, per the Prerequisites note above). Offline behavior (no network calls) confirmed by `tests/unit/test_video_loader_validation.py::test_load_video_makes_no_network_calls`.
- **Scenario 4** (diagnostics emission): PASS with a caveat — exactly one `ExecutionDiagnostics` JSON record is emitted per call, containing all required fields, and the JSON payload itself is valid/parseable. However, the default `loguru` stderr sink prefixes each line with human-readable timestamp/level/location metadata before the JSON message, so a line isn't *purely* JSON as written today (a consumer must extract the trailing `{...}` substring). A dedicated JSON-only sink (e.g. `logger.add(path, serialize=True, format="{message}")`) is a reasonable follow-up before any tooling needs to parse these logs directly, not a blocker for this feature.

Full test suite: 25/25 passed. Coverage gate (`pytest --cov=src/cvip/video --cov-fail-under=100`): **100.00%**.

# Quickstart: Validating the Frame Extraction Service

This is a manual/automated validation guide for the Frame Extraction Service once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/frame_extraction_contract.md](./contracts/frame_extraction_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`).
- Video Loader (`specs/001-video-loader/`) already implemented — this feature requires a `LoadResult`, obtained by calling `load_video()`.
- The existing Video Loader fixtures: `tests/fixtures/video_loader/valid_short.mp4`, `valid_short.mkv`, and `multi_hour.mp4` (regenerate via `python tests/fixtures/video_loader/generate_fixtures.py` if missing). No new fixtures are needed for this feature.

## Scenario 1 — Request frames at a chosen rate (User Story 1)

1. Call `load_video()` on `valid_short.mp4` to get a successful `LoadResult`.
2. Call `extract_frames()` requesting `SamplingMode.FULL`. Expected: every native frame is yielded, each with a correct, sequential `frame_index` and an increasing `timestamp_seconds`.
3. Repeat requesting `SamplingMode.FIXED_INTERVAL` at 1 FPS. Expected: roughly one frame per second of video, per the fixture's known duration.
4. Repeat requesting `SamplingMode.FRAME_LIST` with a specific, unordered list of indices (e.g., `[30, 5, 30, 10]`). Expected: exactly 3 frames yielded (duplicate removed), in ascending index order (5, 10, 30).
5. Repeat requesting `SamplingMode.TIMESTAMP_LIST` with a timestamp that falls between two native frames. Expected: the single nearest decoded frame is yielded — confirm it is a real frame from the video, not an interpolated blend.
6. Call `extract_frames()` with a deliberately `FAILURE` `LoadResult` (e.g., from Video Loader's own rejection-path fixtures). Expected: iterating immediately reports `SOURCE_NOT_VALIDATED`, with no file access attempted.

## Scenario 2 — Memory stays bounded regardless of video length (User Story 2)

1. Extract at `FIXED_INTERVAL` (1 FPS) from `valid_short.mp4` (a few seconds) and record peak memory attributable to the call.
2. Extract at the same rate from `multi_hour.mp4` (3.5 hours) and record peak memory attributable to the call.
3. Expected: both peak-memory figures are at or under 150MB (SC-002) — the multi-hour run does not use meaningfully more memory than the short one.

## Scenario 3 — Progress, cancellation, and resume (User Story 3)

1. Start extraction against `multi_hour.mp4` at `FIXED_INTERVAL` (1 FPS). Partway through, read `FrameExtractor.progress` and confirm it reports a plausible `processed_frames`/`total_frames`/`percent_complete` less than 100%.
2. Call `FrameExtractor.cancel()` (or `break` out of the consuming loop). Expected: iteration stops, and exactly one `ExtractionDiagnostics` record is emitted summarizing the partial run.
3. Note the `frame_index` of the last `FrameContext` received before cancellation. Start a new `extract_frames()` call with `resume_from_frame_index` set to that index + 1. Expected: the first frame yielded is the next one after where the previous run stopped — no frame is re-yielded.
4. Call `extract_frames()` with `resume_from_frame_index` set beyond the video's total frame count. Expected: `RESUME_POINT_OUT_OF_RANGE`, rejected before any frames are yielded.
5. Call `extract_frames()` with both a frame index and a timestamp supplied as the resume point. Expected: the frame index is honored and the timestamp is ignored.

## Scenario 4 — Diagnostics and determinism

1. Run the same `extract_frames()` request against the same fixture twice. Expected: the two runs yield an identical sequence of `frame_index`/`timestamp_seconds` pairs (SC-003).
2. Confirm each of the runs above (Scenarios 1-3) produced exactly one `ExtractionDiagnostics` record — never zero, never more than one per request, regardless of whether the run completed normally, was cancelled, or failed.

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

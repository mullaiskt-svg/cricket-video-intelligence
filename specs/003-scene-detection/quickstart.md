# Quickstart: Validating Scene Detection

This is a manual/automated validation guide for Scene Detection once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/scene_detection_contract.md](./contracts/scene_detection_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`).
- Video Loader (`specs/001-video-loader/`) and the Frame Extraction Service (`specs/002-frame-extraction-service/`) already implemented — this feature requires a `LoadResult` (from `load_video()`) and consumes frames via `extract_frames()`.
- The existing Video Loader fixtures: `tests/fixtures/video_loader/valid_short.mp4`, `valid_short.mkv`, and `multi_hour.mp4` (regenerate via `python tests/fixtures/video_loader/generate_fixtures.py` if missing). No new fixtures are needed for this feature.

## Scenario 1 — Segment a video into scene boundaries (User Story 1)

1. Call `load_video()` on `valid_short.mp4` to get a successful `LoadResult`.
2. Call `detect_scenes()` with a `scene_threshold` matching `config/default.yaml`'s `video.scene_threshold` (27.0) and run it to completion.
3. Expected: `result.boundaries` is a non-`None`, ascending-by-timestamp list (possibly empty, since the fixture is a short synthetic clip); each boundary has a unique `boundary_id`, a `timestamp_seconds`, a `boundary_type`, and a `confidence` in `[0.0, 1.0]`.
4. Call `detect_scenes()` with a deliberately `FAILURE` `LoadResult` (e.g., from Video Loader's own rejection-path fixtures). Expected: `.run()` immediately raises `SOURCE_NOT_VALIDATED`, with no file access attempted.

## Scenario 2 — Distinguish replay-style transitions from ordinary cuts (User Story 2)

1. Run detection against a validated video containing both a known ordinary hard cut and a known replay-style transition (a synthetic or hand-picked segment).
2. Expected: the ordinary cut is reported with `boundary_type = ORDINARY_CUT`; the replay-style transition is reported with `boundary_type = REPLAY_TRANSITION`.
3. Expected: both boundaries carry a `confidence` value — never absent (SC-009) — with the replay-style transition's confidence reflecting how cleanly it matched the gradual-transition heuristic (research.md Decision 2).

## Scenario 3 — Stay within budget, and support clean cancellation (User Story 3)

1. Run detection against `multi_hour.mp4` (3.5 hours) and record elapsed time and peak memory attributable to the call.
2. Expected: elapsed time falls within the module's ~10-20 minute budget share (SC-003); peak memory does not scale with duration in a way that threatens the platform's overall <6GB budget (SC-004).
3. Start a detection run against `multi_hour.mp4` and call `.cancel()` partway through (or have another thread of control request it). Expected: the run stops cleanly, and exactly one `SceneDetectionDiagnostics` record is emitted summarizing the partial run.
4. Confirm the video was read in exactly one forward pass (no re-decoding), consistent with FR-004.

## Scenario 4 — Determinism and diagnostics

1. Run the same `detect_scenes()` request against the same fixture twice. Expected: the two runs yield an identical ordered `boundaries` sequence, including classifications and confidence scores (SC-008).
2. Confirm each of the runs above (Scenarios 1-3) produced exactly one `SceneDetectionDiagnostics` record — never zero, never more than one per request, regardless of whether the run completed normally, was cancelled, or failed.

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

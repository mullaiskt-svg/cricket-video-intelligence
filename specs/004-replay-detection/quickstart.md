# Quickstart: Validating Replay Detection

This is a manual/automated validation guide for Replay Detection once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/replay_detection_contract.md](./contracts/replay_detection_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`).
- Video Loader (`specs/001-video-loader/`), the Frame Extraction Service (`specs/002-frame-extraction-service/`), and Scene Detection (`specs/003-scene-detection/`) already implemented — this feature requires a `LoadResult` and a `SceneDetectionResult` as input.
- The existing Video Loader fixtures: `tests/fixtures/video_loader/valid_short.mp4`, `valid_short.mkv`, and `multi_hour.mp4` (regenerate via `python tests/fixtures/video_loader/generate_fixtures.py` if missing). No new fixtures are needed for this feature.

## Scenario 1 — Detect and score candidate replay segments (User Story 1)

1. Call `load_video()` then `detect_scenes()` on `valid_short.mp4` to get a `LoadResult` and `SceneDetectionResult`.
2. Call `detect_replays()` with the configured weights/threshold/minimum-duration from `config/default.yaml`'s `replay` section, and run it to completion.
3. Expected: `result.segments` is a non-`None`, ascending-by-start-time list (possibly empty, since the fixture is a short synthetic clip); each segment has a unique `replay_id`, `start_seconds`, `end_seconds`, and a `confidence` in `[0.0, 1.0]`.
4. Call `detect_replays()` with a deliberately `FAILURE` `LoadResult`. Expected: `.run()` immediately raises `SOURCE_NOT_VALIDATED`, with no file access attempted.
5. Call `detect_replays()` with a `SceneDetectionResult` for a different video (mismatched `source_video_id`). Expected: `.run()` immediately raises `INVALID_SCENE_DETECTION_RESULT`.
6. Call `detect_replays()` with weights that don't sum to 1.0. Expected: `.run()` immediately raises `INVALID_REPLAY_CONFIGURATION`, with no file access attempted.

## Scenario 2 — Produce a segment list usable across the analyze/generate workflow (User Story 2)

1. Run detection to completion and inspect `result.segments`.
2. Expected: every segment's `replay_id`, `start_seconds`, `end_seconds`, and `confidence` are plain values with no reference back to the `ReplayDetector` instance or the run's internal state — the result can be serialized and handed to a separate process.
3. Expected: `result.source_video_id` matches the video's own `file_hash`, so a later, separate process can confirm the segments belong to the video it's currently working with.

## Scenario 3 — Complete within budget, and follow platform-standard operational behavior (User Story 3)

1. Run detection against `multi_hour.mp4` (3.5 hours) and record elapsed time.
2. Expected: elapsed time falls within the module's ~2-5 minute budget share (SC-004).
3. Confirm the video was read in exactly one forward pass at the configured 1 FPS rate (no re-decoding), consistent with FR-019.
4. Start a detection run against `multi_hour.mp4` and call `.cancel()` partway through. Expected: the run stops cleanly, and exactly one `ReplayDetectionDiagnostics` record is emitted summarizing the partial run.
5. Simulate the source becoming unavailable partway through a run. Expected: `SOURCE_UNAVAILABLE_MID_RUN` is raised, with exactly one diagnostics record emitted.

## Scenario 4 — Determinism and diagnostics

1. Run the same `detect_replays()` request against the same fixture twice. Expected: the two runs yield an identical ordered `segments` sequence, including confidence scores (SC-006).
2. Confirm each of the runs above (Scenarios 1-3) produced exactly one `ReplayDetectionDiagnostics` record — never zero, never more than one per request, regardless of whether the run completed normally, was cancelled, or failed (including a configuration-rejection failure).

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

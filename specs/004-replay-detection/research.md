# Phase 0 Research: Replay Detection

This document resolves the technical questions spec.md's Assumptions deliberately deferred here.

## Decision: Update the `replays` table schema — drop `detection_method`, add `confidence`

**Rationale**: The existing schema (`specs/technical_plan.md`) has `detection_method TEXT CHECK (detection_method IN ('logo', 'scoreboard', 'slowmo'))` — a leftover from an earlier, simpler "pick one detection method" design that predates this feature's actual weighted multi-signal architecture (`config/default.yaml`'s five weights, already locked in). A segment detected via a *combination* of signals has no single "method" to report, and the column can't represent the two signals it doesn't even name (`transition`, `camera_angle`). The column is replaced with `confidence REAL` (0.0-1.0, the combined weighted confidence — this feature's actual output per FR-013), matching the same column already used on `events`. The per-signal breakdown (`Replay Evidence`) is *not* persisted — per spec.md's Assumptions, it's an internal record this feature must preserve for diagnostics/explainability, not a requirement on the public/persisted shape.

`replay_id` is generated by this feature (sequential, unique within a run, starting at 0) and is intended to become the literal SQLite primary key value when the Pipeline Orchestrator persists it (an explicit-PK insert, not an auto-assigned rowid) — so a cross-reference made during detection (e.g., a future Event Detection feature storing "replay_id 3" against an event) remains stable across the persist boundary, fulfilling FR-014's "downstream referencing without repeated timestamp matching" intent.

Updated schema (applied to `specs/technical_plan.md` directly, since this is a cross-cutting document no single feature owns exclusively — same precedent as Scene Detection's and the Frame Extraction Service's own updates there):

```sql
CREATE TABLE replays (
  replay_id INTEGER PRIMARY KEY,
  start_seconds REAL,
  end_seconds REAL,
  confidence REAL,          -- 0.0-1.0, the combined weighted confidence (FR-013)
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**Alternatives considered**:
- **Keep `detection_method`, populate it with the highest-weighted contributing signal**: Rejected — throws away the actual combined-confidence number (this feature's real output, per FR-013/FR-028), and forces an artificial "pick a winner" framing the weighted design was specifically built to avoid.
- **Persist the full `Replay Evidence` breakdown too (a `replay_evidence` table or JSON column)**: Rejected for v1 — spec.md's Assumptions explicitly don't require this; it's tracked in diagnostics instead (FR-025), which is sufficient for the explainability/tuning purpose it exists for without adding new persisted surface area no consumer currently needs.

## Decision: All four self-computed signals sample at the platform's existing 1 FPS rate, not native frame rate

**Rationale**: spec.md's own Assumptions flagged this as unresolved — `specs/technical_plan.md`'s ~2-5 minute budget estimate assumed 1 FPS sampling (Scoreboard OCR's rate), but worried 1 FPS might be too coarse for motion-profile (slow-motion) characterization specifically. Resolved in favor of 1 FPS for all four signals, because motion-profile doesn't need native-rate optical flow to work: broadcast slow-motion replays compress the *same* amount of real-world motion into *more* wall-clock time than live action does, which is still detectable as a **lower average frame-to-frame visual-difference magnitude per elapsed second** even when sampled once per second — the signal is comparative (segment average vs. a live-action baseline average, research.md's next decision), not a measurement of true motion velocity that would require dense native-rate sampling. Empirically, this keeps the whole feature within budget: a 1 FPS full pass over the 3.5-hour benchmark fixture (`multi_hour.mp4`) already measured at ~150-200s in the Frame Extraction Service's own benchmark (`specs/002-frame-extraction-service/`), well inside the ~2-5 minute (120-300s) budget even before this feature's own per-frame CV cost is added. A denser rate (e.g., 5 FPS) was estimated to cost ~9-10 minutes on the same fixture — clearly over budget — and is not adopted without empirical evidence (from the golden dataset, once it exists) that 1 FPS's motion-profile accuracy is actually insufficient in practice.

**Alternatives considered**:
- **Native frame rate (matching Scene Detection's `SamplingMode.FULL`)**: Rejected — 10x+ more target frames than 1 FPS for a typical broadcast, blowing the ~2-5 minute budget by a wide margin (Scene Detection's own full-rate pass took ~16.8 minutes on the same fixture, and that pass does meaningfully less per-frame work than four independent CV signal computations would).
- **A denser-but-not-native rate (e.g., 5 FPS) specifically for motion-profile, 1 FPS for the other three**: Rejected — would require a second, separate Frame Extraction Service pass (violating FR-019's single-decode requirement) or force all four signals up to the denser rate anyway (which itself blows budget, per the estimate above) for no benefit to the other three signals.

## Decision: Scoreboard-absence, motion-profile, and camera-angle are all "differs from a rolling live-action baseline" signals — one shared computational pattern

**Rationale**: None of these three signals has external reference data to compare against (no training set, no "this is what live action always looks like" ground truth for this platform). All three are naturally expressed the same way: as the video is walked forward, the detector maintains a small rolling baseline (recent average ROI content-signature, recent average frame-to-frame difference magnitude, recent average frame "fingerprint") computed *only* from frames outside any currently-open candidate segment, and scores a candidate segment's frames by how much they deviate from that baseline. This is a single reusable mechanism (one "Live-Action Baseline Tracker" concept) applied with three different per-frame measurements, rather than three independently-designed signals — reducing implementation and testing surface, and giving all three the same well-understood behavior (each needs *some* live-action context before it can be meaningfully evaluated; see data-model.md for how the first candidate segment in a video, with no prior baseline, is handled).

Concretely:
- **Scoreboard-region absence**: per-sampled-frame content measure (e.g., edge density / local variance) of the pixels inside `config/default.yaml`'s `ocr.scoreboard_region` ROI, compared against the rolling baseline of that same measure from recent non-candidate frames. A large drop (the region looks emptier/flatter than the established baseline) scores high.
- **Motion profile**: per-sampled-frame whole-frame difference magnitude versus the previous sampled frame (the same style of measurement Scene Detection's own `_frame_diff_score` uses, reused as a pattern, not as shared code — a different module, different purpose), compared against the rolling baseline of that measure. A candidate segment whose average delta is well below the live-action baseline's average delta scores high (characteristic of slow motion).
- **Camera-angle difference**: a cheap, coarse whole-frame descriptor per sampled frame (e.g., a downscaled/blurred version, or a global color-layout summary), compared against the rolling baseline descriptor. A large dissimilarity scores high.

**Alternatives considered**:
- **A pre-trained classifier per signal**: Rejected — no training data exists for this platform, and building/maintaining one is out of proportion to a v1, CPU-only, offline tool.
- **Independent, signal-specific baselines with no shared mechanism**: Rejected — three separate ad hoc implementations of the same underlying "track a rolling live-action baseline, score deviation from it" idea would be pure duplication with no benefit over one shared mechanism.

## Decision: Logo-presence uses OpenCV template matching against an optional configured template

**Rationale**: `config/default.yaml`'s `replay` section has no template-path key yet — this plan adds one (`replay.logo_template_path`, optional, defaulting to unset), consistent with spec.md's Assumption that the template is caller-supplied configuration, not something this feature discovers on its own. When set, each sampled frame's match score against the template (`cv2.matchTemplate`, normalized correlation) is this signal's per-frame score, averaged per FR-029. When unset, the signal always scores 0.0 (FR-015) — no baseline-tracking mechanism is needed here, unlike the other three signals, since there's a concrete reference image to match against directly.

**Alternatives considered**:
- **Generic "any overlay graphic" detection with no configured template**: Rejected — without a reference image, distinguishing "a replay bumper graphic" from other legitimate broadcast overlays (score bugs, sponsor logos, weather graphics) has no principled signal to key on; graceful zero-confidence degradation (already required by FR-015) is the honest answer when no template exists, not a weaker generic heuristic that would likely just add noise.

## Decision: Configuration validation happens lazily inside `.run()`, not at request construction

**Rationale**: FR-022 requires `INVALID_REPLAY_CONFIGURATION` to go through the same fail-fast-with-diagnostics path as every other failure reason in the taxonomy ("fail fast with exactly one of the following reasons... rather than silently returning...") — meaning a diagnostics record must still be emitted for a rejected configuration, the same as for a mid-run decode failure. A constructor-time `raise ValueError` (the pattern Scene Detection's `scene_threshold` validation uses) would never reach the diagnostics-emission path, since the object performing that emission (`ReplayDetector`) wouldn't exist yet. Deliberately deviating from Scene Detection's precedent here: weight/threshold/minimum-duration validation is performed at the start of `ReplayDetector.run()`, using the same `_fail()`-based pattern as every other failure reason, not in `ReplayDetectionRequest.__post_init__`.

**Alternatives considered**:
- **Constructor-time `ValueError`, matching Scene Detection's `scene_threshold` precedent**: Rejected for this specific case — Scene Detection's single scalar threshold check doesn't need a diagnostics record (spec.md never asked for one there), but FR-022 explicitly lists `INVALID_REPLAY_CONFIGURATION` as a taxonomy value alongside failures that clearly do need one, and the spec doesn't carve out an exception for the configuration case.

## Decision: Cooperative cancellation and diagnostics reuse follow Scene Detection's exact pattern

**Rationale**: `ReplayDetector` is a blocking `.run()` call (not a pull-based iterator), exactly like `SceneDetector` — the same reasoning from `specs/003-scene-detection/research.md` applies unchanged: `.cancel()` sets a flag `run()`'s loop checks each iteration, with cleanup (resource release, one diagnostics record) happening when the loop notices and falls through, not synchronously within `.cancel()` itself. Diagnostics reuse `cvip.common.diagnostics`'s `ExecutionDiagnostics`/`DiagnosticsTracker`, module_name `"video.replay_detection"`.

**Alternatives considered**: None — no reason to diverge from an already-established, working pattern for the same structural shape of problem.

## Decision: Module location is `src/cvip/video/`, not a new subpackage

**Rationale**: This feature's inputs (`LoadResult`, `extract_frames()`, Scene Detection's result type) already live in `cvip.video`; every consumer of this feature already depends on that subpackage regardless of where the detector itself lives. New files use a `replay_detection_*` naming prefix, following the exact precedent set when Scene Detection was added alongside the Frame Extraction Service and Video Loader.

**Alternatives considered**: None beyond what `specs/002-frame-extraction-service/research.md` and `specs/003-scene-detection/research.md` already settled for the same question — no new information changes that reasoning here.

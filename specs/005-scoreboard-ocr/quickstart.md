# Quickstart: Validating Scoreboard OCR

This is a manual/automated validation guide for Scoreboard OCR once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/scoreboard_ocr_contract.md](./contracts/scoreboard_ocr_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`), including `pytesseract` — confirm the native Tesseract binary is also installed and on `PATH` (`tesseract --version`; see `docs/DEPENDENCIES.md` if not).
- Video Loader (`specs/001-video-loader/`) and the Frame Extraction Service (`specs/002-frame-extraction-service/`) already implemented — this feature requires only a `LoadResult` as input (it does not depend on Scene Detection's or Replay Detection's output).
- The existing Video Loader fixtures: `tests/fixtures/video_loader/valid_short.mp4`, `valid_short.mkv`, and `multi_hour.mp4` (regenerate via `python tests/fixtures/video_loader/generate_fixtures.py` if missing). No new fixtures are needed for this feature.

## Scenario 1 — Extract a complete, never-failing raw scoreboard timeline (User Story 1)

1. Call `load_video()` on `valid_short.mp4` to get a `LoadResult`.
2. Call `extract_scoreboard()` with the configured ROI/preprocessing/`min_confidence` from `config/default.yaml`'s `ocr` section, and run it to completion.
3. Expected: `result.samples` has one entry per frame sampled at the platform's configured rate, ordered by ascending timestamp; every sample has both `ocr_confidence` and `parse_confidence` in `[0.0, 1.0]`.
4. Construct a scenario where the scoreboard ROI is genuinely obscured for a stretch (e.g., a synthetic frame sequence with the ROI blanked out). Expected: those samples have `ocr_confidence = 0.0` and empty `raw_text`, and the run still completes normally.
5. Construct a scenario with a reading whose `wickets` decreases from the prior accepted reading (not accompanied by a matching `runs` drop, so the innings-transition heuristic doesn't apply). Expected: that sample has `parse_confidence = 0.0`, and its `OCREvidence.validation_failure_reason` is `WICKETS_DECREASED`.
6. Call `extract_scoreboard()` with a deliberately `FAILURE` `LoadResult`. Expected: `.run()` immediately raises `SOURCE_NOT_VALIDATED`, with no file access attempted.
7. Call `extract_scoreboard()` with `min_confidence` set to `1.5`. Expected: `.run()` immediately raises `INVALID_OCR_CONFIGURATION`, with no file access attempted.

## Scenario 2 — Produce a timeline usable by a later, separate module (User Story 2)

1. Run extraction to completion and inspect `result.samples`.
2. Expected: every sample's fields are plain values with no reference back to the `ScoreboardOcrExtractor` instance or the run's internal state (including the ROI-unchanged-skip and last-accepted-reading tracker state) — the result can be serialized and handed to a separate process.
3. Expected: `result.source_video_id` matches the video's own `file_hash`.
4. Confirm a sample with `parse_confidence = 0` is treated by a consuming test double as unusable for deriving an event, rather than the consumer attempting its own reinterpretation of `raw_text`.

## Scenario 3 — Complete within budget, and follow platform-standard operational behavior (User Story 3)

1. Run extraction against `multi_hour.mp4` (3.5 hours) and record elapsed time.
2. Expected: elapsed time falls within the module's ~15-25 minute budget share (SC-004) — record the observed ratio of Tesseract calls actually made versus samples produced (research.md Decision 1's skip mechanism) as a data point for future tuning.
3. Confirm the video was read in exactly one forward pass at the configured 1 FPS rate (no re-decoding), consistent with FR-024.
4. Start an extraction run against `multi_hour.mp4` and call `.cancel()` partway through. Expected: the run stops cleanly, and exactly one `ScoreboardOcrDiagnostics` record is emitted summarizing the partial run.
5. Simulate the source becoming unavailable partway through a run. Expected: `SOURCE_UNAVAILABLE_MID_RUN` is raised, with exactly one diagnostics record emitted.

## Scenario 4 — Determinism and diagnostics

1. Run the same `extract_scoreboard()` request against the same fixture twice. Expected: the two runs yield an identical ordered `samples` sequence, including both confidence fields (SC-006) — this must hold even for samples served via the ROI-unchanged skip.
2. Confirm each of the runs above (Scenarios 1-3) produced exactly one `ScoreboardOcrDiagnostics` record — never zero, never more than one per request, regardless of whether the run completed normally, was cancelled, or failed (including a configuration-rejection failure).

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

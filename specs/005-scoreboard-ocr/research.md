# Phase 0 Research: Scoreboard OCR

This document resolves the technical questions spec.md's Assumptions deliberately deferred here.

## Decision: Skip the Tesseract call when the scoreboard ROI is pixel-unchanged from the previous sample — not parallelization, not a reduced sampling rate

**Rationale**: `specs/technical_plan.md` flags this feature as the platform's single largest budget cost (~15-25 minutes of the ~40-minute ceiling) from ~12,600 Tesseract calls (one per sampled second) on a 3.5-hour match, and spec.md explicitly deferred the mitigation choice to this planning phase. Two candidate mitigations were evaluated and rejected before landing on this one:

- **Parallelizing Tesseract calls across CPU cores**: rejected as the *primary* mitigation. The constitution names the target hardware explicitly — an Intel Core i3-1115G4, a **2-core/4-thread** part. Splitting ~12,600 independent Tesseract calls across only 2 physical cores caps the realistic speedup at roughly 2x (thread-level parallelism doesn't help CPU-bound OCR work much beyond physical core count), which alone doesn't reliably close a ~15-25 minute gap to a comfortable margin, and adds real implementation complexity (process/thread pool management, ensuring FR-020's determinism still holds when results are gathered back in order).
- **Sampling below the platform's 1 FPS rate, with a future Smoother module covering the gaps**: rejected. Reducing temporal resolution directly risks missing a real scoring event that happens to fall in an unsampled second (two boundaries in quick succession, a wicket right at a sampling boundary) — a correctness risk for SC-011's downstream accuracy target, not just a performance tradeoff. `specs/technical_plan.md`'s own list of candidate mitigations treats this as a last resort, and this feature has no way to know *in advance* which seconds are safe to skip.
- **Chosen instead — reuse the previous sample when the ROI hasn't visually changed**: the on-screen scoreboard graphic is static for the great majority of the time between scoring events (typically tens of seconds per delivery, versus the instant the graphic updates). Before running Tesseract on a sampled frame, compute a cheap whole-ROI difference against the *previous sampled frame's* ROI (a plain `cv2.absdiff(...).mean()` over the raw, pre-preprocessing crop — the same style of lightweight comparison Replay Detection's own motion-profile signal already uses, reused as a pattern, not shared code). If the difference is below a small tolerance (accounting for video-compression noise on an otherwise-static graphic), skip the Tesseract call entirely and reuse the previous sample's parsed fields, `raw_text`, `ocr_confidence`, and `OCREvidence` verbatim for the new timestamp — the underlying pixels are (near-)identical, so re-running Tesseract would deterministically produce the same result anyway, and FR-020's determinism requirement holds because the skip decision itself is a deterministic function of the two frames' pixel content. This still produces exactly one `ScoreboardSample` per sampled frame (FR-006) at full 1 FPS temporal resolution — nothing about the *output* changes, only how much Tesseract work produces it. Worst case (a broadcast whose ROI never repeats, e.g., a constantly-animating graphic in the same region), this degrades gracefully to the original ~15-25 minute baseline, which was already within budget per `specs/technical_plan.md`'s own estimate — this mitigation is a strict improvement with no downside case.

**Alternatives considered**: (see rejected options above). A hybrid (skip check *and* light parallelization of the calls that do run) was also considered but deferred — the skip alone is expected to be sufficient, and adding process-pool machinery for a 2-core target with modest remaining call volume is complexity not currently justified; revisit only if benchmark results on the multi-hour fixture show it's still needed.

## Decision: Per-field OCR confidence comes from `pytesseract.image_to_data()`, not a second OCR pass

**Rationale**: FR-029 requires preserving per-field OCR confidence "where the OCR engine provides it." Tesseract exposes confidence at the word level via `pytesseract.image_to_data(image, output_type=Output.DICT)`, which returns, for each recognized word/token: its text, a confidence (0-100), and its bounding box within the image — in one single call, no separate pass needed. The parser (structured-parsing stage, FR-030) maps recognized word tokens to fields positionally/by pattern (e.g., a token matching `\d+/\d+` near the expected runs/wickets position becomes the `runs`/`wickets` pair; a token matching `\d+\.\d+` becomes the over/ball reading). Each field's confidence in `OCREvidence` is the confidence of whichever token(s) the parser attributed to it; a field the parser couldn't confidently attribute to any single token is left absent in the per-field breakdown (spec.md Assumptions), not fabricated. The overall `ocr_confidence` (the public, always-present field) is the mean confidence across all non-empty recognized tokens in the ROI for that frame, or `0.0` if no tokens were recognized at all (folding into FR-010's "undetectable region" case). `raw_text` is the concatenation of all recognized tokens in their detected reading order.

**Alternatives considered**:
- **`pytesseract.image_to_string()` for `raw_text` plus a separate `image_to_data()` call for confidence**: rejected — two calls per frame would double Tesseract's already-dominant cost for no benefit; `image_to_data()` alone provides both the text (by concatenating its `text` column) and the confidences in one call.
- **A single overall confidence with no per-field breakdown**: rejected — this was the spec's original shape before the review round that added FR-029; per-field confidence is now an explicit requirement.

## Decision: Preprocessing order is grayscale → upscale → threshold

**Rationale**: `config/default.yaml`'s `ocr.preprocess` block lists `grayscale`, `threshold`, `upscale` as configuration flags/values (whether each step is applied, and the upscale factor), not a prescribed execution order. Standard OCR preprocessing practice (and Tesseract's own documentation guidance) is to binarize (threshold) *after* enlarging, not before: thresholding a small image first and then enlarging the already-binary result with an interpolation method tends to introduce blocky/jagged edges that hurt character recognition, whereas enlarging the grayscale image first (with a smooth interpolation) and thresholding the larger version preserves more edge detail for Tesseract to work with. Order chosen: convert to grayscale (if enabled) → upscale by the configured factor (`cv2.resize` with `INTER_CUBIC` or `INTER_LINEAR`, if enabled) → apply thresholding (Otsu's automatic threshold, if enabled) — each step individually skippable per its own config flag, consistent with FR-004's caller-supplied preprocessing settings. This is a tunable implementation detail, not a contract guarantee; revisit if golden-dataset results (SC-011) suggest a different order performs better for this platform's actual broadcast footage.

**Alternatives considered**:
- **Threshold before upscale**: rejected per the reasoning above (jagged edges after enlarging an already-binary image); kept as a documented, easily-swappable choice rather than a hardcoded assumption baked into the contract.

## Decision: The innings-transition heuristic and rule validation run as one dedicated validation stage, comparing only against a single retained "last accepted reading"

**Rationale**: FR-012/FR-013/FR-014 (validate against the most recent *accepted* reading; suppress monotonic checks when wickets and runs both drop) only require retaining **one** prior reading's numeric fields at a time (runs, wickets, over_number, ball_in_over) — not a longer history — since every comparison is against "the most recent accepted reading," and an accepted reading immediately replaces whatever was retained before it. This keeps the validation stage's internal state trivial (four numbers, updated in place) and matches this platform's established "rolling, not full-history" state-tracking pattern (e.g., Replay Detection's Live-Action Baseline Tracker also only retains rolling aggregates, not per-frame history).

**Alternatives considered**:
- **Retaining a short window of recent readings (e.g., last 5) for a more robust innings-transition signal**: rejected for v1 — spec.md's FR-014 heuristic (wickets AND runs both drop) only needs the immediately preceding accepted reading to evaluate, and a longer window adds state and complexity for a robustness improvement not called for in the spec; revisit only if the golden dataset shows the single-prior-reading heuristic misfires often in practice.

## Decision: `pytesseract` must be installed in this dev environment before implementation begins

**Rationale**: `pytesseract==0.3.10` is already pinned in `requirements.txt`, and the native Tesseract binary is already installed and documented (`docs/DEPENDENCIES.md`, verified present in this environment at v5.5.3), but the `pytesseract` Python package itself is not currently installed in the active virtual environment (`pip show pytesseract` reports not found). This is a setup step for `/speckit-implement` (`pip install -r requirements.txt` or a targeted `pip install pytesseract`), not a design decision, but is called out here so it isn't discovered as a surprise mid-implementation.

**Alternatives considered**: None — this is a missing-install gap, not a technical choice.

## Decision: Cooperative cancellation and diagnostics reuse follow the established platform pattern

**Rationale**: `ScoreboardOcrExtractor` is a blocking `.run()` call (not a pull-based iterator), exactly like `SceneDetector` and `ReplayDetector` — the same reasoning from `specs/003-scene-detection/research.md` and `specs/004-replay-detection/research.md` applies unchanged: `.cancel()` sets a flag `run()`'s loop checks each iteration, with cleanup (resource release, one diagnostics record) happening when the loop notices and falls through, not synchronously within `.cancel()` itself. Diagnostics reuse `cvip.common.diagnostics`'s `ExecutionDiagnostics`/`DiagnosticsTracker`, module_name `"video.scoreboard_ocr"`. Configuration validation (ROI, preprocessing settings, `min_confidence`) happens lazily inside `.run()`, not at request construction — matching Replay Detection's own precedent (research.md), since FR-018 requires `INVALID_OCR_CONFIGURATION` to go through the same diagnostics-emitting `_fail()` path as every other failure reason.

**Alternatives considered**: None — no reason to diverge from an already-established, working pattern for the same structural shape of problem.

## Decision: Module location is `src/cvip/video/`, not a new subpackage

**Rationale**: This feature's only input (`LoadResult`, `extract_frames()`/`FrameContext`) already lives in `cvip.video`; every consumer of this feature already depends on that subpackage regardless of where the extractor itself lives. New files use a `scoreboard_ocr_*` naming prefix, following the exact precedent set by Scene Detection and Replay Detection.

**Alternatives considered**: None beyond what `specs/002-frame-extraction-service/research.md`, `specs/003-scene-detection/research.md`, and `specs/004-replay-detection/research.md` already settled for the same question — no new information changes that reasoning here.

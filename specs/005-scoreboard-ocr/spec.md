# Feature Specification: Scoreboard OCR

**Feature Branch**: `005-scoreboard-ocr`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "Scoreboard OCR: extracts the raw, per-second scoreboard timeline from a validated cricket broadcast video, consuming frames exclusively through the Frame Extraction Service (Module 1a) at the platform's configured 1 FPS rate (config/default.yaml's video.sample_fps) -- never opening the video file directly, per this platform's established convention (Scene Detection, Replay Detection). For each sampled frame, this feature reads the configured scoreboard region (config/default.yaml's ocr.scoreboard_region, an (x, y, width, height) ROI as fractions of frame dimensions) using Tesseract OCR via the pytesseract wrapper, after applying the configured preprocessing steps (grayscale, threshold, upscale factor). These ROI and preprocessing settings are caller-supplied through the request object, not read from the config file by this feature itself. From the raw OCR text, this feature parses: runs, wickets (a count, 0-10), the over-and-ball reading (split into over_number and ball_in_over), batter (striker), non-striker, bowler, and run_rate. It does NOT attempt to track or infer innings number. This feature produces exactly one ScoreboardSample record per sampled frame -- never skips a frame outright, even on a bad reading. Two distinct confidence fields are always populated: ocr_confidence and parse_confidence. A single noisy or unreadable second of scoreboard footage must never abort or fail the run; instead readings are recorded as-is with low confidence, or with parse_confidence=0 if they violate cricket-scoring rules against the immediately preceding reading. This feature still fails fast with a specific typed reason on genuinely structural problems: an unvalidated LoadResult, an invalid configuration, and mid-run failures surfaced by the Frame Extraction Service. Output is an ordered, in-memory sequence of ScoreboardSample values, following the same precedent Scene Detection and Replay Detection both established of returning results in-memory rather than writing to the database themselves. Performance is a first-class concern given Tesseract's dominant cost in the platform's budget; mitigation strategy is resolved during this feature's own /speckit-plan research phase. Must run fully offline, CPU-only, and emit the platform's standardized one-record-per-run execution diagnostics."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Extract a complete, never-failing raw scoreboard timeline (Priority: P1)

A pipeline run needs the raw, per-second scoreboard readings (runs, wickets, over/ball, players, run rate) for the whole match, so that a later module can detect scoring events by diffing consecutive readings. A single badly-lit, obscured, or misread second must never derail the rest of a multi-hour analysis.

**Why this priority**: This is the entire reason the feature exists — without a complete raw timeline, Event Detection has nothing to diff. The "never hard-fail on one bad reading" behavior is what makes the timeline complete in practice, not just in principle.

**Independent Test**: Can be fully tested by running Scoreboard OCR against a validated video containing a mix of clearly-readable scoreboard frames, a stretch where the scoreboard region is genuinely obscured (e.g., during a graphic overlay), and a frame whose text is noisy enough to misparse, and confirming every sampled frame still produces exactly one `ScoreboardSample`, with confidence fields correctly reflecting each case.

**Acceptance Scenarios**:

1. **Given** a validated match video, **When** Scoreboard OCR runs, **Then** it produces exactly one `ScoreboardSample` per frame sampled at the platform's configured rate, ordered by ascending timestamp, each carrying both an `ocr_confidence` and a `parse_confidence` value.
2. **Given** a sampled frame where the configured scoreboard region is not visually detectable (e.g., obscured by a graphic), **When** Scoreboard OCR evaluates it, **Then** it records a sample with `ocr_confidence = 0.0` and empty raw text, rather than failing the run.
3. **Given** a sampled frame whose OCR reading falls below the configured minimum confidence, **When** Scoreboard OCR evaluates it, **Then** it records the reading as-is with its low `ocr_confidence`, without discarding or attempting to correct it.
4. **Given** a parsed reading whose runs, wickets, over number, or ball-in-over value violates basic cricket-scoring rules against the immediately preceding *accepted* reading (see Assumptions for how a likely innings transition is distinguished from a genuine misread), **When** Scoreboard OCR evaluates it, **Then** it records the reading with `parse_confidence = 0.0` rather than fabricating a corrected value.
5. **Given** the very first reading of a run, **When** Scoreboard OCR evaluates it, **Then** it is never rejected by the rule-consistency check, since no prior reading exists to compare against.
6. **Given** a video that has not been successfully validated (no successful `LoadResult`), **When** Scoreboard OCR is requested, **Then** it refuses and does not attempt to read the file.

---

### User Story 2 - Produce a timeline usable by a later, separate module (Priority: P2)

Event Detection (Module 5) runs later in the same `cvip analyze` invocation, consuming this feature's output to derive scoring events by diffing consecutive readings.

**Why this priority**: This is what makes the raw timeline actually consumable — but it builds on User Story 1's sample sequence rather than being useful on its own.

**Independent Test**: Can be fully tested by confirming the result's shape carries everything a later module needs to diff consecutive readings and identify the source video, without any in-memory state from the OCR run itself still being required.

**Acceptance Scenarios**:

1. **Given** a completed OCR run, **When** its result is inspected, **Then** every sample's fields are self-contained plain values (not references to in-memory objects from the run), suitable for handing to a persistence layer that outlives this process.
2. **Given** a completed OCR run, **When** its result is inspected, **Then** it includes a source-video identifier consistent with the platform's existing identifier convention (Video Loader's `file_hash`).
3. **Given** a completed OCR run's samples, **When** a downstream module (Event Detection) consumes them, **Then** it treats a sample with `parse_confidence = 0` as unusable for deriving an event, rather than attempting its own correction or reinterpretation of the raw text.

---

### User Story 3 - Complete within budget, and follow platform-standard operational behavior (Priority: P3)

An operator runs Scoreboard OCR as part of analyzing a full 3-4 hour match. It completes within its allotted share of the overall analysis budget despite being the platform's single most expensive stage, fails fast with a specific reason if it cannot proceed, and produces the same standardized diagnostics record every other module does.

**Why this priority**: A hard platform constraint that must hold before this module can be trusted as a pipeline stage — but it is a property of User Story 1 operating at real-world scale, not a new extraction capability of its own.

**Independent Test**: Can be fully tested by running extraction against a full-length (3-4 hour) validated video and confirming elapsed time stays within budget; separately, by forcing each of the taxonomy's failure conditions and confirming the matching specific reason is raised along with exactly one diagnostics record; separately, by confirming a malformed configuration is rejected before any frame is processed.

**Acceptance Scenarios**:

1. **Given** a 3-4 hour match video, **When** Scoreboard OCR runs, **Then** it completes within its allotted share of the overall analysis budget (`specs/technical_plan.md` Performance Targets).
2. **Given** a match video, **When** Scoreboard OCR runs, **Then** the video is decoded no more than once during the run.
3. **Given** the underlying video becomes unavailable partway through extraction, **When** this occurs, **Then** the run fails fast with the specific `SOURCE_UNAVAILABLE_MID_RUN` reason rather than silently returning an incomplete timeline as if it were complete.
4. **Given** a configuration with a malformed scoreboard ROI, invalid preprocessing settings, or an out-of-range minimum confidence, **When** Scoreboard OCR is requested, **Then** it is rejected immediately with `INVALID_OCR_CONFIGURATION`, before any frame is processed.
5. **Given** any extraction run (successful, cancelled, or failed), **When** it completes, **Then** exactly one diagnostics record is emitted summarizing the run.

### Out of Scope

- Tracking or inferring innings number. The scoreboard graphic alone is not reliably distinguishable across broadcasters as "innings 1 vs innings 2" without additional context; this feature leaves that field unpopulated (see Assumptions).
- Smoothing, interpolating, or otherwise cleaning the raw timeline. This feature reports readings exactly as observed (including low-confidence and rule-violating ones); a separate, future module is responsible for producing a cleaned sequence.
- Deriving scoring events from the timeline. This feature only produces raw per-second readings — comparing consecutive readings to detect a four, six, or wicket belongs to Event Detection (Module 5).
- Writing to the database. Like every other module on this platform, this feature returns an in-memory result; persisting it to the `scoreboard_readings` table is the Pipeline Orchestrator's responsibility.
- Determining highlight-worthiness or replay classification of any reading or moment.

### Edge Cases

- What happens when the scoreboard region is not visually detectable in a given frame? — Resolved: recorded with `ocr_confidence = 0.0` and empty raw text, not a hard failure (US1 Acceptance Scenario 2).
- What happens when OCR's own character-recognition confidence is below the configured minimum? — Resolved: recorded as-is with its low `ocr_confidence`; downstream smoothing owns discounting or interpolating over it (US1 Acceptance Scenario 3).
- What happens when a parsed reading's numeric fields violate cricket-scoring rules against the immediately preceding reading? — Resolved: recorded with `parse_confidence = 0.0` rather than a fabricated correction (US1 Acceptance Scenario 4).
- What happens at the boundary between two innings, where wickets and runs legitimately drop rather than misread? — Resolved: see Assumptions for the heuristic distinguishing a likely innings transition from a genuine misread, and its documented limitation.
- What happens to the very first reading of a run, which has no prior reading to compare against? — Resolved: it cannot fail the rule-consistency check (US1 Acceptance Scenario 5).
- What happens when the configured scoreboard ROI, preprocessing settings, or minimum confidence are themselves invalid? — Resolved: rejected immediately with `INVALID_OCR_CONFIGURATION`, before any frame is processed (US3 Acceptance Scenario 4).
- What happens when the underlying video becomes unavailable partway through extraction? — Resolved: fails fast with the specific `SOURCE_UNAVAILABLE_MID_RUN` reason (US3 Acceptance Scenario 3).
- What happens when a batter/non-striker/bowler name is misread but still parses to *some* text? — Resolved: text fields carry no *historical* rule-consistency check (see Assumptions); a name merely differing from the prior reading does not cause `parse_confidence = 0`.
- What happens when a batter/non-striker/bowler field cannot be structurally parsed at all (e.g., the OCR text where a name should be is empty or unusable)? — Resolved: recorded as a `PLAYER_PARSE_FAILED` validation failure and does cause `parse_confidence = 0` (FR-030, FR-031, Assumptions).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST accept a successful `LoadResult` (from the Video Loader feature) as input and MUST NOT accept a raw file path directly, nor attempt its own file validation.
- **FR-002**: System MUST NOT produce any scoreboard samples for a `LoadResult` that does not indicate a successful, validated video.
- **FR-003**: System MUST source the frames it analyzes through the Frame Extraction Service (Module 1a), at the platform's configured sampling rate, by consuming its shared `FrameContext` abstraction directly (the same one Scene Detection and Replay Detection already consume) — not a raw frame array or a type of its own — consistent with every other computer-vision module on this platform.
- **FR-004**: System MUST accept the scoreboard region (ROI), preprocessing settings (grayscale/threshold/upscale), and a minimum OCR-confidence threshold as caller-supplied request configuration, not read from a config file internally.
- **FR-005**: System MUST use Tesseract OCR to read the configured scoreboard region of each sampled frame, after applying the configured preprocessing steps.
- **FR-006**: System MUST produce exactly one `ScoreboardSample` per sampled frame — it MUST NOT skip a frame outright regardless of reading quality.
- **FR-007**: System MUST extract, where present in the raw OCR text, the following fields: runs, wickets, over_number, ball_in_over, batter (striker), non_striker, bowler, and run_rate.
- **FR-008**: System MUST NOT attempt to track or infer innings number; that field remains unpopulated by this feature (see Assumptions).
- **FR-009**: System MUST populate two distinct confidence fields on every sample — `ocr_confidence` (Tesseract's own character-recognition confidence for the raw text) and `parse_confidence` (confidence the raw text parsed into a valid, cricket-rule-consistent reading) — never absent.
- **FR-010**: System MUST record a sample with `ocr_confidence = 0.0` and empty raw text when the configured scoreboard region is not visually detectable in a frame, rather than failing the run.
- **FR-011**: System MUST record a reading exactly as observed (including a low `ocr_confidence`) when OCR's own confidence falls below the configured minimum, rather than discarding, correcting, or hard-failing on it.
- **FR-012**: System MUST validate a parsed reading's numeric fields (runs, wickets, over_number, ball_in_over) against the most recent *accepted* reading this run has produced — where a reading is **accepted** when it has been successfully structurally parsed (see FR-030) and carries `parse_confidence > 0` — not against the immediately preceding reading regardless of its own acceptance, so that a single rule-violating or unparseable reading cannot cascade into repeated false rejections of otherwise-valid subsequent readings.
- **FR-013**: Wickets MUST never decrease and MUST remain within 0-10; runs MUST never decrease; over_number MUST never decrease; ball_in_over MUST fall within a valid range, and MUST NOT decrease relative to the last accepted reading while over_number stays the same (e.g., a prior reading of over 12 ball 5 followed by over 12 ball 3 is rejected, even though over_number alone didn't decrease) — except when the comparison itself looks like a likely innings transition (see FR-014 and Assumptions), in which case these monotonic checks are suppressed for that one comparison only.
- **FR-014**: System MUST treat a reading whose wickets AND runs both drop relative to the immediately preceding accepted reading as a likely innings transition, and MUST NOT apply the runs/wickets/over_number monotonic checks (FR-013) to that one comparison — this is a heuristic, not innings-awareness (FR-008), and carries the documented limitation in Assumptions.
- **FR-015**: A reading that violates an applicable monotonic rule from FR-013 MUST be recorded with `parse_confidence = 0.0` rather than a fabricated corrected value.
- **FR-016**: The first reading with `parse_confidence > 0` in a run (i.e., one with no prior accepted reading to compare against) MUST NOT be rejected by the rule-consistency checks in FR-013.
- **FR-017**: System MUST validate the configured scoreboard region, preprocessing settings, and minimum OCR confidence before processing any frame, and MUST reject an invalid configuration with `INVALID_OCR_CONFIGURATION` rather than silently clamping or ignoring the discrepancy.
- **FR-018**: System MUST fail fast with exactly one of the following specific reasons whenever extraction cannot proceed correctly, rather than silently returning an incomplete timeline as if it were genuine: `SOURCE_NOT_VALIDATED` (the supplied `LoadResult` is not a successful, validated video), `INVALID_OCR_CONFIGURATION` (the configured ROI, preprocessing settings, or minimum confidence are invalid), `SOURCE_UNAVAILABLE_MID_RUN` (the video becomes inaccessible after extraction has begun), or `DECODE_FAILURE_MID_RUN` (a frame fails to decode partway through an otherwise-successful run).
- **FR-019**: System MUST support cooperative cancellation of an active extraction run. On cancellation, the system MUST stop processing further frames, MUST release any resources it holds, and MUST still emit exactly one diagnostics record summarizing the partial run.
- **FR-020**: System MUST produce the identical ordered sample sequence (including both confidence fields) for the same video and the same configuration on every run (deterministic output).
- **FR-021**: System MUST emit exactly one standardized execution diagnostics record per run, containing: frames processed, count with an undetectable scoreboard region, average `ocr_confidence` across all samples, count with `ocr_confidence` below the configured minimum, average `parse_confidence` across all samples, count with `parse_confidence = 0` (rule/parse validation failures, broken down by reason per FR-031 where practical, including any suppressed by the innings-transition heuristic), count of samples served via the ROI-unchanged-skip optimization (i.e., reused from the previous sample rather than freshly OCR'd), the platform's configuration version (mirroring Scene Detection's own `configuration_version` precedent), and processing duration.
- **FR-022**: System MUST NOT itself persist results to any database table — it returns an in-memory result; persistence is the Pipeline Orchestrator's responsibility.
- **FR-023**: System MUST NOT derive scoring events, determine highlight-worthiness, or classify replay footage — those decisions belong to Event Detection, Event Ranking, and Replay Detection respectively.
- **FR-024**: System MUST decode the video no more than once during an extraction run.
- **FR-025**: System MUST perform extraction using only local resources, with no network or cloud calls.
- **FR-026**: System MUST perform extraction using CPU only, with no dependency on GPU hardware.
- **FR-027**: Timestamps MUST be reported as `timestamp_seconds` (a real number of seconds), regardless of the units the frame's native timestamp arrives in.
- **FR-028**: The reported sample sequence MUST be self-contained (all fields plain values, plus a source-video identifier consistent with the platform's existing identifier convention) such that a separate, later process can consume it without any in-memory state from the extraction run itself.
- **FR-029**: System MUST preserve an internal OCR Evidence record for every sampled frame, capturing: the raw OCR text, a reference to the preprocessed image, the OCR engine's overall confidence, per-field OCR confidence where the OCR engine provides it (runs, wickets, over_number, ball_in_over, batter, non_striker, bowler, run_rate), the parser's structured output, and the validation result (including a specific reason when validation failed — see FR-031). This record is for diagnostics, debugging, explainability, and future OCR tuning; it is retained internally by the implementation and is not required to be part of the public `ScoreboardSample` shape.
- **FR-030**: System MUST treat OCR text extraction, structured field parsing, and cricket-rule validation as three distinct, independently-identifiable processing stages (Frame → OCR → Raw Text → Structured Parsing → Cricket Rule Validation → `ScoreboardSample`). A frame's fields are **structurally parsed** when the parsing stage produces a well-formed value for each field it could locate in the raw text (the specific bar for "well-formed" per field, e.g. a numeric field must actually parse as a number, is an implementation detail for `/speckit-plan`) — this determination is what FR-012's "accepted reading" test depends on, and it MUST be distinguishable, via the OCR Evidence record, from a downstream rule-validation failure rather than the two being conflated into a single opaque confidence number. A reading where a field essential to producing a valid, usable reading (e.g., the batter field) cannot be structurally parsed at all MUST also be recorded with `parse_confidence = 0.0`, alongside the FR-013 monotonic-rule violations — both are causes of the same public outcome, distinguished only by the internal reason recorded per FR-031.
- **FR-031**: When a reading's `parse_confidence` is reduced to 0.0 — whether because of a rule-consistency violation (FR-013) or because a field essential to producing a valid reading could not be structurally parsed at all (FR-030) — System MUST record the specific reason in the OCR Evidence's validation result. At minimum: `RUNS_DECREASED`, `WICKETS_DECREASED`, `INVALID_OVER_SEQUENCE`, `INVALID_BALL_NUMBER`, `PLAYER_PARSE_FAILED` — and the taxonomy MUST NOT preclude adding further reasons in the future.

### Key Entities

- **Scoreboard Sample**: A single per-frame raw reading — this feature's public output unit. Key attributes: `timestamp_seconds`, `runs`, `wickets`, `over_number`, `ball_in_over`, `batter`, `non_striker`, `bowler`, `run_rate`, `raw_text`, `ocr_confidence` (0.0-1.0, always present), `parse_confidence` (0.0-1.0, always present).
- **OCR Evidence**: An internal record of how one sample's fields and confidence values were reached (FR-029) — not part of the public `Scoreboard Sample` shape, but preserved by the implementation for diagnostics, debugging, explainability, and future OCR tuning (spec.md Assumptions). Key attributes: raw OCR text, a reference to the preprocessed image, overall OCR confidence, per-field OCR confidence where available (runs, wickets, over_number, ball_in_over, batter, non_striker, bowler, run_rate), the parser's structured output, and the validation result (a pass/fail per applicable check, plus the specific `Validation Failure Reason` when a check failed).
- **Validation Failure Reason**: The taxonomy of *why* a reading's `parse_confidence` was reduced to 0.0, recorded internally in the OCR Evidence (FR-031) — at minimum `RUNS_DECREASED`, `WICKETS_DECREASED`, `INVALID_OVER_SEQUENCE`, `INVALID_BALL_NUMBER`, `PLAYER_PARSE_FAILED`. Distinct from `Scoreboard OCR Failure Reason` below, which covers run-level structural failures, not per-reading validation outcomes.
- **Scoreboard OCR Request**: A caller's request configuration. Key attributes: the validated video (`LoadResult`) to analyze, the scoreboard region (ROI), preprocessing settings, and the minimum OCR confidence (validated per FR-017).
- **Scoreboard OCR Result**: The complete, ordered output of one extraction run for one video. Key attributes: a source-video identifier, the ordered list of Scoreboard Samples, and total sample count — self-contained enough to be consumed by a later module (FR-028).
- **Scoreboard OCR Diagnostics**: The standardized per-run record summarizing one complete (or cancelled) extraction run (FR-021). Key attributes: frames processed, undetectable-scoreboard-region count, average `ocr_confidence`, low-`ocr_confidence` count, average `parse_confidence`, `parse_confidence = 0` count (with a breakdown by `Validation Failure Reason` where practical), count served via the ROI-unchanged-skip optimization, the platform's configuration version, processing duration, and failure reason (if applicable).
- **Scoreboard OCR Failure Reason**: The failure taxonomy for this feature — `SOURCE_NOT_VALIDATED`, `INVALID_OCR_CONFIGURATION`, `SOURCE_UNAVAILABLE_MID_RUN`, `DECODE_FAILURE_MID_RUN` — distinct from every other module's own taxonomy on this platform.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A consuming pipeline module (Event Detection) can obtain a full, ordered, self-contained raw scoreboard timeline for a validated video without implementing any of its own OCR or frame-reading logic.
- **SC-002**: Every produced sample includes both an `ocr_confidence` and a `parse_confidence` value between 0.0 and 1.0 inclusive — never absent.
- **SC-003**: A frame whose scoreboard region is undetectable, or whose reading is noisy or rule-inconsistent, never causes the run to fail — in 100% of test cases, the run still produces a complete sample sequence covering the whole video.
- **SC-004**: Scoreboard OCR for a 3-4 hour match completes within its allotted share of the platform's overall analysis time budget on target-class hardware, in 100% of test runs.
- **SC-005**: The video is decoded no more than once per extraction run, in 100% of test runs.
- **SC-006**: Given the same video and configuration, repeated extraction runs produce identical ordered sample sequences (including both confidence fields) 100% of the time.
- **SC-007**: Every extraction run produces exactly one diagnostics record, regardless of whether every reading was clean or many were low-confidence or rule-violating.
- **SC-008**: Extraction completes using only local, offline resources on target-class hardware (CPU-only, 8GB RAM class machine) in 100% of test runs.
- **SC-009**: A configuration with a malformed scoreboard ROI, invalid preprocessing settings, or an out-of-range minimum confidence is rejected before any frame is processed, in 100% of test cases.
- **SC-010**: A reading whose runs, wickets, over_number, or ball_in_over violates the applicable monotonic rule against the immediately preceding accepted reading is recorded with `parse_confidence = 0`, in 100% of constructed test cases (this criterion is independently verifiable by unit/integration tests; it does not depend on the golden dataset).
- **SC-011**: When measured against a hand-annotated reference match (the platform's golden dataset, `specs/technical_plan.md`'s "Golden Dataset & Accuracy Verification" standard), this feature's readings are accurate and complete enough to let Event Detection meet the constitution's ≥95% detection accuracy target for fours/sixes/wickets. This criterion depends on the golden dataset existing — a cross-cutting platform concern tracked separately, not something this feature alone can satisfy through unit/contract/integration testing.

## Assumptions

- **Innings tracking is out of scope (FR-008)**: the scoreboard graphic alone is not reliably distinguishable across broadcasters as "which innings" without additional context this feature doesn't have. The `innings` column in `specs/technical_plan.md`'s `scoreboard_readings` table is left unpopulated by this feature; a future module or the Pipeline Orchestrator would need to derive it if ever required.
- **Innings-transition heuristic (FR-014)**: because this feature has no innings-awareness, a genuine innings change (where wickets and runs both legitimately reset to a lower value) would otherwise be indistinguishable from a garbled misread under a strict "never decrease" rule. The chosen heuristic — suppress the monotonic checks for one comparison when *both* wickets and runs drop together — is a deliberate, documented trade-off: it correctly tolerates real innings transitions, but a misread that *coincidentally* drops both values in the same way would also be waved through unflagged (a known, accepted limitation, not a correctness bug this feature is expected to close; downstream consumers already treat `parse_confidence` as one input among several, not an absolute guarantee).
- **`ball_in_over` range**: assumed to be the integer parsed from the fractional part of the broadcast's "over.ball" display (e.g., "12.3" → `ball_in_over = 3`), valid in the 0-6 range (a value of 6, or an occasional extra ball due to a no-ball/wide, is tolerated, not treated as a rule violation) — the exact parsing approach is an implementation detail for `/speckit-plan`, not this spec's concern.
- **`run_rate` carries no monotonic check**: unlike runs/wickets/overs, a current run rate can legitimately rise or fall over the course of an innings (e.g., after a maiden over or a boundary-heavy over), so no "never decreases" rule applies to it.
- **Text fields carry no *historical* rule-consistency check, but do carry a structural one**: `batter`, `non_striker`, and `bowler` are never compared against a prior reading (there is no "previous name" to violate) — a name that simply differs from the last reading (a genuine substitution, or a plausible-looking misread) does not cause `parse_confidence = 0`. However, a name field that cannot be structurally parsed at all (FR-030) — e.g., the OCR text where a name should be is empty or unusable — is recorded as a `PLAYER_PARSE_FAILED` validation failure (FR-031) and does cause `parse_confidence = 0`, the same as a numeric monotonic-rule violation.
- **Per-field OCR confidence depends on OCR engine support**: FR-029's per-field confidence in the OCR Evidence record is preserved "where the OCR engine provides it" — Tesseract can report confidence at the word/character level, but mapping a word-level confidence back to a specific structured field (e.g., "this word is the wickets count") is the parser's job, and is only as precise as the parser's own field-boundary detection; a field whose confidence can't be cleanly attributed is left absent in the per-field breakdown rather than assigned a fabricated value.
- **`min_confidence`'s role is informational, not corrective**: falling below the configured minimum changes nothing about the stored reading itself (FR-011) — it is only reflected in the diagnostics record's low-confidence count (FR-021), leaving discounting or interpolation to a future, separate smoothing module.
- **Performance mitigation strategy is a planning-phase decision**: `specs/technical_plan.md` flags this feature as the platform's single largest budget cost (~15-25 minutes of the ~40-minute ceiling, from ~12,600 Tesseract calls on a 3.5-hour match) and explicitly calls for evaluating mitigations beyond the already-assumed "crop to ROI, sample at 1 FPS" baseline. This spec intentionally does not choose a specific mitigation (e.g., parallelizing Tesseract calls, or a perceptual-hash-based skip when the ROI is unchanged from the previous sample) — that technical decision, and verification that the chosen approach still meets FR-020's determinism requirement, is `/speckit-plan`'s to resolve, the same way Replay Detection's own sampling-density tension was resolved during its planning phase rather than pre-decided in its spec.
- **Tesseract/pytesseract are existing, not new, prerequisites**: the native Tesseract binary and the `pytesseract` wrapper are already documented platform dependencies (`docs/DEPENDENCIES.md`, `requirements.txt`); this feature is their first actual consumer, not the reason they were added.
- This feature inherits Video Loader's input constraints by depending on its `LoadResult` (MP4/MKV containers, video already fully saved to local disk, not a live stream), and the Frame Extraction Service's own sampling conventions.

## Parser Extension Architecture (post-implementation amendment)

**Background**: `specs/011-club-broadcast-overlay-support/`'s amendment introduced a `_ScoreParser` Strategy interface as a private implementation detail of `scoreboard_ocr.py`, to let a second broadcast overlay format (the club-broadcast compound-score format) be parsed without touching the original format's own parsing logic. A third, independent match recording (WILD WANDERERS VS PHOENIX FIREHAWKS -- different club, different resolution/codec lineage) was found to use a *third*, still-different overlay layout (a bare, standalone score token, separate from a bare over.ball token immediately followed by its own total-overs token -- neither the original format's `/`-separated tokens nor the club format's single fused compound token). Rather than add a third one-off parser as another private implementation detail, this amendment promotes the existing Strategy interface to a first-class, documented, public extension point, and implements the third format as its first real test of that promotion.

**This is architectural reorganization, not a redesign**: `GenericBroadcastParser` and `ClubBroadcastParser`'s own parsing logic is byte-for-byte unchanged (moved, not rewritten); `scoreboard_ocr.py`'s ROI extraction, preprocessing, Tesseract invocation, cricket-rule validation, and diagnostics are unaffected in behavior; `ScoreboardSample`'s public shape is unchanged. The only genuinely new public surface is the extension point itself.

**The architecture** (`src/cvip/video/scoreboard_parsers.py`):

- `ScoreboardParser`: a public `Protocol` every format-specific parser implements. Two class-level metadata attributes (`name`, a short stable identifier; `description`, a human-readable summary of the token shape it recognizes) plus two methods (`matches(tokens) -> bool`, `parse(tokens) -> (parsed_fields, field_confidences)`). Implementations must be pure functions of `tokens` alone -- no shared mutable state, no dependency on prior readings, no dependency on any other registered parser.
- `PARSERS`: an ordered tuple of parser instances. `GenericBroadcastParser` (the universal fallback -- `matches()` always returns `True`) must always be last; order between specific parsers is immaterial in practice, since their `matches()` signatures are mutually exclusive by construction (verified in `tests/contract/test_scoreboard_parsers_contract.py`), but is still fixed for determinism.
- `select_parser(tokens)`: iterates `PARSERS` in order, returns the first whose `matches()` accepts the reading's tokens. Deterministic and side-effect-free.

**Diagnostics** (`scoreboard_ocr.py`'s `ExecutionDiagnostics`): `input_summary` now includes a `parser_registry` field -- every registered parser's `name` and `description`, emitted once per run -- alongside the pre-existing `output_summary`'s `parser_strategy` breakdown (how many readings each parser actually claimed). Together these answer "which parsers were even available this run, what does each one claim to detect, and which one actually got selected, how often" without reading source code.

**Extension guide -- adding support for a new broadcast overlay format**:

1. Implement `ScoreboardParser` in `scoreboard_parsers.py`: a `name`, a `description`, a `matches(tokens)` predicate distinguishing this format's token shape from every other registered parser's, and a `parse(tokens)` method populating whichever fields (`runs`/`wickets`/`over_number`/`ball_in_over`/`batter`/`non_striker`/`bowler`/`run_rate`) can be reliably extracted -- a field with no reliably-attributable token is left absent, never fabricated (the same "documented heuristic limitation, not solved perfectly" precedent `ClubBroadcastParser`'s striker heuristic and `SeparateTokenBroadcastParser`'s missing batter/non-striker extraction both already establish).
2. Add an instance to the `PARSERS` tuple, before `GenericBroadcastParser`.
3. Write parser-specific unit tests (`tests/unit/test_scoreboard_parsers.py`) against real captured token shapes -- not synthesized guesses (see `SeparateTokenBroadcastParser`'s own tests, built from a direct per-token OCR capture against real footage, for the pattern).
4. Confirm the six architectural invariants in `tests/contract/test_scoreboard_parsers_contract.py` still hold: every parser (including the new one) successfully parses its own canonical tokens; existing parsers are behaviorally unaffected by the new registration; `GenericBroadcastParser` remains the sole, final fallback; registration is purely additive (no existing parser's source needs to change); selection stays deterministic; the registry has no duplicate or ambiguous (mutually-matching) registrations.

No existing parser's source, and no line of `scoreboard_ocr.py`'s OCR pipeline, needs to change to add a new format.

**`SeparateTokenBroadcastParser`** (the third format, this amendment's concrete instance of the above): score (`{runs}-{wickets}`, e.g. `"12-0"`) and over/ball/total-overs (`{over}.{ball}` immediately followed by its own `({total_overs})` token, e.g. `"1.0"` `"(20)"`) are separate tokens, disambiguated from the visually-identical-shaped bowler-figures token (`{wickets}-{runs}` immediately followed by its own `(overs)` token, e.g. `"0-12"` `"(1)"`) positionally -- the score always precedes the over/ball pair in this broadcast's observed left-to-right layout, bowler figures always follow it. Batter/non-striker are **not** extracted by this parser: that screen region produced unrecognizable OCR noise (e.g. `"SK4"`, `"SKY"`, `"S$Ke"`) across every real sample examined during its design -- a known limitation, documented rather than guessed at, consistent with this platform's established precedent of disclosing a heuristic's actual limits. Bowler name and current run rate are extracted best-effort (bowler: a name immediately preceding its own stats marker, tolerating exactly one short non-alphabetic "icon glyph" token observed consistently between the two; run rate: a labeled `"CRR:"` convention). Given Event Detection derives FOUR/SIX/WICKET purely from `runs`/`wickets` deltas (per `specs/007-event-detection/spec.md`) and only uses `batter` for a WICKET event's secondary attribution, this is the same scope-narrowing precedent `specs/011-club-broadcast-overlay-support/` already established: the fields Event Detection actually depends on are the priority, not full-fidelity extraction of every on-screen field.

## Separate-Token Regex Noise Tolerance (post-implementation amendment)

**Background**: after `specs/007-event-detection/spec.md`'s State Transition Detection amendment isolated Event Detection's comparison logic as verifiably correct, a real-match recall re-run (5.3%, unchanged from before that amendment) pointed the bottleneck upstream: on the Wild Wanderers vs Phoenix Firehawks match, 81.5% of raw OCR samples had at least one null core field, and `generic_broadcast` (the universal fallback) was selected for 75.7% of samples despite this broadcast's actual format being `separate_token_broadcast`. A real-frame token capture (`ground_truth_v2/inspect_generic_fallback_frames.py`, pulling and re-processing actual frames from the source video, not synthesized tokens) found the cause: `SeparateTokenBroadcastParser.matches()`'s sole detection signature -- the over.ball token immediately followed by its own `"(total_overs)"` token, both matched with strict `^...$` regexes -- broke whenever Tesseract glued a single stray character onto either side of that pairing (a trailing comma on the over.ball token: `"7.0,"`; a trailing bracket/brace on the parenthetical: `"(20)]"`, `"(20)}"`; a leading stray character on the score token itself: `"(90-5"`). In every one of these captured cases, the actual score token (`"76-0"`, `"96-1"`, `"131-6"`) was cleanly, correctly read by Tesseract -- but the whole reading was discarded anyway, because the format-detection anchor lived on a different, more fragile part of the overlay than the value actually needed downstream.

**The fix**: `_SEPARATE_SCORE_RE`, `_SEPARATE_OVER_BALL_RE`, and `_PAREN_TOTAL_OVERS_RE` (`scoreboard_parsers.py`) are now anchored only where doing so is load-bearing (the digit sequence itself) -- tolerating exactly one leading stray character on the score token, and arbitrary trailing noise on the over.ball/total-overs tokens -- mirroring `ClubBroadcastParser`'s own `_COMPOUND_SCORE_RE` precedent (already using `.search()` specifically to tolerate a leading noise character, documented in that regex's own comment). This is a targeted loosening, not a move to unanchored substring search everywhere: a genuinely different-shaped token (a name, a CRR/RRR label) still never matches, and the six architectural invariants (`tests/contract/test_scoreboard_parsers_contract.py`) still hold unchanged.

**Preprocessing warm-up fix (PR #13 review finding)**: the warm-up-then-lock strategy selection (`scoreboard_preprocessing.py`, `ScoreboardOcrExtractor._advance_preprocessing_warmup`) originally preprocessed every warm-up-window frame with `DEFAULT_STRATEGY_NAME` (Otsu) only, and permanently locked to Otsu if `PREPROCESSING_WARMUP_SAMPLE_LIMIT` samples passed without a specific parser confidently matching. This was self-defeating for exactly the formats this platform's other preprocessing strategy (`adaptive_mean`) exists for: a heterogeneous-background overlay's frames are precisely the ones Otsu binarizes badly, so they were also precisely the ones least likely to produce a specific-parser match during warm-up under Otsu -- an unlucky run of early frames could lock Otsu in permanently even though `adaptive_mean` would have recognized the format from the very first frame. Fixed: while still warming up, if a frame's Otsu-preprocessed reading falls through to `GenericBroadcastParser` with no `runs`/`wickets` extracted at all (i.e. genuinely nothing usable, not merely "the working original format also legitimately routes through the generic fallback"), the extractor now also trials every other registered strategy against that same frame before counting it as a spent warm-up sample -- bounded to the warm-up window, not every frame, so the steady-state single-OCR-call-per-frame performance property this module's docstring commits to is unchanged. Verified by the full `tests/unit/test_scoreboard_ocr_validation.py` suite (including the mixed-strategy-run diagnostics test) and `tests/unit/test_scoreboard_parsers.py`; not yet re-measured against a full real-match run.

**What this does not fix**: a token where the OCR literally drops a character rather than adding a stray one -- e.g. the opening `"("` merged away entirely into the next word (`"20).Mukesh"`) -- has no `"(digits)"` substring left to find at all, regardless of how tolerant the regex is. This remains a real, undocumented-no-longer miss (`tests/unit/test_scoreboard_parsers.py`'s `test_paren_total_overs_re_does_not_match_when_opening_paren_is_missing` asserts this explicitly, so the boundary of the fix stays visible in the test suite rather than silently assumed).

**Impact measurement** (same real match, same video, OCR re-extracted from scratch -- `third_match_raw_ocr_v2.csv` before vs. `third_match_raw_ocr_v4.csv` after; ~112 minutes OCR extraction time, unchanged):

| Metric | Before | After |
|---|---|---|
| Raw OCR samples with a null core field | 81.5% (9,313/11,434) | 67.7% (7,740/11,434) |
| `separate_token_broadcast` parser share | 22.0% (2,511/11,434) | 36.3% (4,156/11,434) |
| Distinct score states (Event Detection) | 33 | 37 |
| Total events detected | 4 | 11 (FOUR=7, SIX=1, WICKET=2, TEAM_MILESTONE=1) |
| Innings transitions detected | 0 | 1 |
| Recall vs. 57 ground-truth events | 5.3% (3/57) | **14.0% (8/57)** |
| False positives (scoring events) | 0 | 2 |
| Precision (scoring events) | 100% (3/3) | 80% (8/10) |

This is a genuine, isolated improvement directly attributable to this one fix (Event Detection's own logic, per the State Transition Detection amendment above, was not touched again for this measurement) -- recall roughly tripled. It is also not close to resolved: `generic_broadcast` still accounts for the majority (63.7%) of samples on this broadcast, and the two new false positives (a WICKET detected where the ground truth expected a FOUR at a nearby over/ball; an early-second-innings FOUR with no matching ground-truth event nearby) indicate real remaining OCR noise, not just missing coverage. The residual gap traces to frame-level failures this fix cannot reach by construction (a dropped character, not an added one; or a frame where the score panel itself is not legibly captured at all) -- root-causing those is separate, further OCR-quality work, not a comparison-logic or parser-architecture concern.

## Fused Over.Ball Token Recovery (post-implementation amendment, round 2)

**Background**: per this amendment's own stated boundary above, a systematic follow-up investigation (`ground_truth_v2/classify_generic_fallback_v4.py`) pulled real frames at an evenly-spread sample of the residual `generic_broadcast`/no-score population (still 61.1%, 6,985/11,434 samples, after the round-1 fix above) and classified, against `SeparateTokenBroadcastParser`'s actual matching logic, *why* each one still fails -- re-processed under `adaptive_mean`, the strategy the real run actually locks to for this match, not a guess. Of 200 classified frames: 35.0% had neither a score nor an over.ball token at all (likely genuine scene content -- motion blur, cuts, or non-scoreboard graphics -- not yet visually confirmed); 29.0% had a bare over.ball token but no recognizable paren sibling; **22.0% had the over.ball token and its own `(total_overs)` token fused into a single token** (e.g. Tesseract dropping the space between them entirely: `"0.0"` + `"(20)"` -> `"0.0,(20)"`); the remainder were a mix of score-without-over-ball, fully illegible frames, and video-seek imprecision in the investigation tooling itself (tracked and excluded, not a real failure mode).

**The fix**: `_find_split_over_ball_index()`'s two-*separate*-tokens requirement can never recover the fused case, since the second token it looks for was merged away rather than merely noisy -- no amount of per-side regex tolerance (round 1's fix) reaches this. Added `_FUSED_OVER_BALL_PAREN_RE` and `_locate_over_ball()` (`scoreboard_parsers.py`): the latter tries the existing two-token split shape first (the common, cleaner case), falling back to a single-token fused-shape match (over.ball digits, up to 3 stray characters, then a literal `"(total_overs)"` still embedded in the same token) if the split shape isn't found. `SeparateTokenBroadcastParser.matches()`/`.parse()` now go through `_locate_over_ball()` instead of `_find_split_over_ball_index()` directly; every downstream token-position scan (score lookup, bowler-figures lookup) is unaffected, since both shapes resolve to a single token index either way.

**What this does not fix**: same boundary as round 1's fix, restated for the fused case -- a token where the *opening paren itself* was dropped or merged away, not just glued to its neighbor (two real observed cases, `"0.05120)"` and `"0.57120)"`, both with no `"("` substring left anywhere), has nothing left to recover. `tests/unit/test_scoreboard_parsers.py`'s `test_fused_over_ball_paren_re_rejects_when_opening_paren_is_missing` asserts this explicitly against both real captured tokens.

**Impact measurement** (same 200-frame sample, `adaptive_mean`, before vs. after this fix -- a targeted re-classification, not a full pipeline re-run):

| Metric | Before | After |
|---|---|---|
| `over_ball_and_paren_fused_into_one_token` (unrecovered) | 22.0% (44/200) | 15.0% (30/200) |
| Frames recovered by this fix | -- | 14/200 (7.0% of the full residual-failure sample) |

14 of the 44 fused-token failures in this sample are now recognized (the remaining 30 are the "opening paren itself missing" case above, correctly still unrecovered). Extrapolated to the full match's 6,985-sample residual population, this is a meaningful but partial recovery -- roughly 7% of currently-failing samples, not a resolution of the 61.1% failure rate. Not yet re-measured as an end-to-end recall/precision number: that requires a fresh ~112-minute full OCR pass, which this investigation did not re-run. The `bare_over_ball_present_but_no_paren_sibling_at_all` (29.0%) and `neither_score_nor_over_ball_token_present` (35.0%) buckets are unaffected by this fix and remain open -- the former's real examples turned out to be a mix of genuinely-recoverable corrupted-paren cases and the classification script's own false positives (an unrelated CRR value coincidentally token-shaped like an over.ball reading), so a fix there needs more individual frame review before writing another regex change, not a repeat of this same targeted-loosening approach without first separating signal from classifier noise.

## Bare-Sibling Total-Overs Token Recovery (post-implementation amendment, round 3)

**Background**: round 2 explicitly deferred the `bare_over_ball_present_but_no_paren_sibling_at_all` bucket (29.0%) pending individual frame review, since it was suspected to be a mix of real signal and classifier false positives. `ground_truth_v2/investigate_missing_paren_sibling.py` pulled the *full* token list (not a 3-example sample) for every frame in that bucket across a 300-timestamp survey, first filtering out CRR:/RRR:-preceded false matches (13 of 124, a genuine run-rate value coincidentally token-shaped like an over.ball reading). Of the 111 remaining genuine cases, the single most common real shape by a wide margin was neither round 2's fused-token case nor the documented "opening paren merged into the next word" case: it's a total-overs token that **is still its own separate, correctly-positioned token immediately after the over.ball token, but has lost exactly its opening `"("` character** while keeping its digits and closing bracket intact -- e.g. `"13.3"` then `"20)"`, `"14.0"` then `"20}"`, `"18.0"` then `"20]"`. At least 16 of the 111 examples showed this exact clean shape on manual review, likely more (not exhaustively hand-verified past that point).

**The fix**: `_PAREN_TOTAL_OVERS_RE` requires the literal `"("` unconditionally, however much trailing noise around it is already tolerated -- it can never match a token that never had one in the first place. Added `_BARE_TOTAL_OVERS_RE` (`^(\d{1,2})[\)\]\}]`, tolerant of `)`/`]`/`}` as the closing character, matching the bracket-substitution variety already observed) and `_find_bare_sibling_over_ball_index()`, wired into `_locate_over_ball()` as a third fallback shape, tried after the existing split and fused shapes both fail. Scoped narrowly (1-2 digits, a closing bracket, checked only as the token immediately following an already-confirmed over.ball-shaped token) to keep the false-positive surface the same as the existing `_find_split_over_ball_index` precedent it extends -- verified against `HAPPY_PATH_TOKENS`/`CLUB_EVIDENCE_TOKENS` in the contract test suite, neither of which contains a token shaped this way.

**What this does not fix**: a small minority of the 111 examples had further degradation this fix doesn't reach -- the total-overs digits themselves misread (`"20"` -> `"zo"`, a letter/digit confusion), the bracket character entirely absent (bare `"20"` with nothing after it), or the over.ball token itself carrying a leading stray character (`"'3.0"`, `"}15.3"`) that `_SEPARATE_OVER_BALL_RE` has no tolerance for (unlike `_SEPARATE_SCORE_RE`'s existing one-leading-character allowance). None of these were pursued this round -- each would need its own real-frame frequency count before deciding whether it's worth the added false-positive surface, the same discipline this round applied to round 2's deferred bucket.

**Impact measurement** (same 200-frame sample used in round 2, `adaptive_mean`, cumulative with round 2's fix already applied):

| Metric | Baseline (no round-2/3 fix) | After round 2 only | After round 2 + round 3 |
|---|---|---|---|
| Now-recognized (no longer generic_broadcast) | 5.5% (11/200) | 12.5% (25/200) | **19.0% (38/200)** |
| `bare_over_ball_present_but_no_paren_sibling_at_all` (unrecovered) | 29.0% (58/200) | 29.0% (58/200) | 23.0% (46/200) |

Round 3 alone recovers 12 more samples in its target bucket (58 -> 46); combined with round 2, 27 of 200 residual-failure samples in this fixed sample (13.5%) are now recognized that weren't before either fix -- roughly triple round 2's standalone gain. Same caveat as round 2: not yet re-measured as an end-to-end recall/precision number against a fresh full OCR pass. The `neither_score_nor_over_ball_token_present` (35.0%) bucket remains completely untouched and unexplained -- likely genuine non-scoreboard scene content, but not yet visually confirmed against the actual frames.

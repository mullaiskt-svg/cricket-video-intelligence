# Quickstart: Validating OCR Timeline Smoother

This is a manual/automated validation guide for the OCR Timeline Smoother once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/ocr_timeline_smoother_contract.md](./contracts/ocr_timeline_smoother_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`) — no new dependency is introduced by this feature (research.md).
- Scoreboard OCR (`specs/005-scoreboard-ocr/`) already implemented — this feature requires only a `ScoreboardOcrResult` as input.
- **No video fixtures needed.** Unlike every prior module, this feature never touches a video file — all test scenarios below are built from synthetic `ScoreboardOcrResult`/`ScoreboardSample` instances constructed directly in Python (plan.md Project Structure).

## Scenario 1 — Produce a fully diffable, gap-free scoreboard timeline (User Story 1)

1. Construct a raw timeline with a stretch of consecutive samples flagged unusable by Scoreboard OCR (`ocr_confidence = 0` or `parse_confidence = 0`), preceded by at least one usable sample. Call `smooth_timeline()` and run it to completion.
2. Expected: each unusable sample's cleaned output fields equal the most recently established known-good reading's fields (FR-003).
3. Construct a raw timeline where a single usable sample's core scoring tuple (`runs`, `wickets`, `over_number`, `ball_in_over`) disagrees with an otherwise-consistent run of `outlier_window` usable neighbors on both sides.
4. Expected: that sample is treated as an outlier and its cleaned output fields equal the surrounding consensus value (FR-004).
5. Construct a raw timeline where two or more *consecutive* usable samples all agree on a new, divergent core scoring tuple (a genuine change).
6. Expected: none of those samples are treated as outliers — each is passed through with its own field values (spec.md Edge Cases).
7. Construct a raw timeline whose leading several samples are all unusable, with no known-good reading established yet.
8. Expected: those leading samples' cleaned output fields are all `null` (FR-006) — never a fabricated value.
9. Construct a raw timeline with no unusable samples and no outliers at all.
10. Expected: the cleaned output is identical to the input's field values, sample for sample (US1 AS4).
11. For any of the above, confirm `result.samples` has exactly one entry per input sample, in the same order, at the same timestamps (US1 AS5, FR-007).

## Scenario 2 — Produce a timeline usable by a later, separate module (User Story 2)

1. Run smoothing to completion and inspect `result.samples`.
2. Expected: every sample's fields are plain values with no reference back to the `OCRTimelineSmootherRunner` instance or the run's internal state (including the known-good tracker and outlier-flag state) — the result can be serialized and handed to a separate process (FR-019).
3. Expected: `result.source_video_id` matches `scoreboard_ocr_result.source_video_id` (FR-019).

## Scenario 3 — Complete quickly, and follow platform-standard operational behavior (User Story 3)

1. Construct a synthetic ~12,600-sample sequence (a full match's worth) and run smoothing against it, recording elapsed time.
2. Expected: elapsed time is under 1 minute (SC-008), matching `specs/technical_plan.md`'s Performance Targets entry for this stage.
3. Call `smooth_timeline()` with a missing or structurally malformed `scoreboard_ocr_result` (e.g., `None`, or samples out of timestamp order). Expected: `.run()` immediately raises `INVALID_INPUT`, with no sample processed.
4. Call `smooth_timeline()` with `outlier_window` set to `0`. Expected: `.run()` immediately raises `INVALID_SMOOTHING_CONFIGURATION`, with no sample processed.
5. Start a smoothing run against the ~12,600-sample sequence and call `.cancel()` partway through. Expected: the run stops cleanly, and exactly one `OCRTimelineSmootherDiagnostics` record is emitted summarizing the partial run.

## Scenario 4 — Determinism and diagnostics

1. Run the same `smooth_timeline()` request against the same constructed input twice. Expected: the two runs yield an identical ordered `samples` sequence (FR-016, SC-005).
2. Confirm each of the runs above (Scenarios 1-3) produced exactly one `OCRTimelineSmootherDiagnostics` record — never zero, never more than one per request, regardless of whether the run completed normally, was cancelled, or failed (including a configuration-rejection failure) (FR-017, SC-006).

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

# Quickstart: Validating Event Detection

This is a manual/automated validation guide for Event Detection once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/event_detection_contract.md](./contracts/event_detection_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`) — no new dependency is introduced by this feature (research.md).
- OCR Timeline Smoother (`specs/006-ocr-timeline-smoother/`), Scoreboard OCR (`specs/005-scoreboard-ocr/`), and Replay Detection (`specs/004-replay-detection/`) already implemented — this feature requires an `OCRTimelineSmootherResult`, a `ScoreboardOcrResult`, and a `ReplayDetectionResult` as input.
- **No video fixtures needed.** Like the OCR Timeline Smoother, this feature never touches a video file — all test scenarios below are built from synthetic result instances constructed directly in Python (plan.md Project Structure).

## Scenario 1 — Detect scoring events without manual video scrubbing (User Story 1)

1. Construct a cleaned timeline where the team's `runs` increases by 4 on a single-ball advance (`ball_in_over` +1, same `over_number`) with no `wickets` change. Call `detect_events()` and run it to completion.
2. Expected: a `FOUR` `DetectedEvent` at that reading's `timestamp_seconds`/`over_number`/`ball_in_over` (FR-004).
3. Repeat with a `runs` increase of 6. Expected: a `SIX` event (FR-005).
4. Construct a cleaned timeline where `wickets` increases by 1, with `runs` also changing in the same comparison. Expected: a `WICKET` event only — no `FOUR`/`SIX` also emitted for that comparison (FR-006, FR-007, FR-023).
5. Construct a cleaned timeline where `ball_in_over` rolls over from 5 to 0 with `over_number` incrementing, and `runs` increases by 4 across that rollover. Expected: still recognized as a valid single-ball advance and a `FOUR` is emitted (FR-006a).
6. Construct a cleaned timeline with no `runs`/`wickets` change between consecutive readings. Expected: no event emitted for that comparison (Acceptance Scenario US1-4).
7. Construct a cleaned timeline containing a leading gap (all-`null` core fields). Expected: no event derived from any comparison involving a `null`-valued reading (FR-009, SC-006).

## Scenario 2 — Team milestone detection (User Story 2)

1. Construct a cleaned timeline where the team's `runs` crosses 50 between two consecutive readings. Expected: exactly one `TEAM_MILESTONE` event with `milestone_value = 50` (FR-008, FR-026).
2. Construct a cleaned timeline where a single comparison's `runs` delta crosses two thresholds at once (e.g., 45 → 106 with the default 50-run interval). Expected: two `TEAM_MILESTONE` events, `milestone_value = 50` and `milestone_value = 100` (Acceptance Scenario US2-2).
3. Construct a cleaned timeline where `runs` stays above an already-crossed threshold for many subsequent readings. Expected: no additional `TEAM_MILESTONE` for that threshold again (Acceptance Scenario US2-3).
4. Construct a cleaned timeline where a single-ball 4-run advance also crosses a milestone threshold. Expected: both a `FOUR` and a `TEAM_MILESTONE` event are emitted for that one comparison (FR-023 orthogonality).

## Scenario 3 — Reliable, queryable persisted events (User Story 3)

1. Construct a raw `ScoreboardOcrResult` with two readings bracketing a detected delta, one with `ocr_confidence = 0.9` and the other with `parse_confidence = 0.6`. Run detection. Expected: the corresponding event's `confidence` is `0.6` (FR-014, Acceptance Scenario US3-1).
2. Construct a `ReplayDetectionResult` with a segment overlapping one detected event's timestamp. Expected: that event's `is_replay` is `true`; every other event's `is_replay` is `false` (FR-016, Acceptance Scenarios US3-2/US3-3).
3. Inspect a detected `WICKET` event's `importance`. Expected: it equals `config/default.yaml`'s `events.ranking.WICKET` value (FR-015, Acceptance Scenario US3-4).
4. Confirm the `WICKET` event's `player` equals the dismissed batter's name (the reading immediately before the dismissal), not the bowler (FR-013).

## Scenario 4 — Explainability, precedence, and determinism

1. Run detection and inspect the internal `EventEvidence` for a detected event. Expected: it records the bracketing readings, deltas, raw confidence inputs consulted, replay-match result, milestone threshold(s) crossed (if any), and which rule fired (FR-024).
2. Construct a cleaned timeline matching the innings-transition heuristic (both `runs` and `wickets` dropping). Expected: no `FOUR`/`SIX`/`WICKET`/`TEAM_MILESTONE` from that comparison, and the next event's `innings` reflects the increment (FR-010, FR-011).
3. Run the same `detect_events()` request against the same constructed input twice. Expected: identical ordered `events` sequence, including identical `event_key` values (FR-021, FR-025, SC-005, SC-007).
4. Construct a synthetic ~12,600-sample cleaned timeline (a full match's worth) and run detection against it, recording elapsed time. Expected: elapsed time is under 1 minute (SC-004).
5. Call `detect_events()` with a missing or structurally malformed input (any of the three results). Expected: `.run()` immediately raises `INVALID_INPUT`, with no comparison processed.
6. Call `detect_events()` with `team_milestone_interval` set to `0`. Expected: `.run()` immediately raises `INVALID_DETECTION_CONFIGURATION`, with no comparison processed (FR-029).
7. Start a detection run against the ~12,600-sample timeline and call `.cancel()` partway through. Expected: the run stops cleanly, and exactly one `EventDetectionDiagnostics` record is emitted summarizing the partial run, including its `output_summary` fields (FR-028).
8. Construct a cleaned timeline with no `runs`/`wickets` change anywhere (zero events detected) and run detection to completion. Expected: the run succeeds normally, and its diagnostics `output_summary` reports `average_confidence=0.0` — never a crash (FR-028).

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

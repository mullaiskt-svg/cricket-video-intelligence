# Quickstart: Validating Clip Generator

This is a manual/automated validation guide for Clip Generator once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/clip_generator_contract.md](./contracts/clip_generator_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed (`pip install -r requirements-dev.txt`) — no new dependency is introduced by this feature (research.md).
- No upstream module needs to be implemented first — this feature's input is a `DetectedEvent`-shaped sequence, built directly in Python (research.md Decision 7 — a structural, not hard, dependency on Module 5).
- **No video, database, or frame fixtures needed.** Like Event Detection, this feature never touches a video file — all test scenarios below are built from synthetic event records constructed directly in Python (plan.md Project Structure).

## Scenario 1 — Turn selected events into playable clip windows (User Story 1)

1. Construct one event at `timestamp_seconds=120.0`, `is_replay=False`, with `pre_roll_seconds=8`, `post_roll_seconds=12`, `video_duration_seconds=3600`. Call `generate_clips()` and run it to completion.
2. Expected: `plan.clips` has one `PlannedClip` with `clip_start_seconds=112.0`, `clip_end_seconds=132.0`, `event_count=1`, `merged=False` (FR-002, Acceptance Scenario US1-1).
3. Construct an event at `timestamp_seconds=3.0` with the same 8s pre-roll (would compute `clip_start_seconds=-5.0`). Expected: clamped to `0.0` (FR-003, Acceptance Scenario US1-2).
4. Construct an event near `video_duration_seconds` such that `timestamp_seconds + post_roll_seconds` exceeds it. Expected: `clip_end_seconds` clamped to `video_duration_seconds` (FR-003, Acceptance Scenario US1-3).
5. Call `generate_clips()` with an empty `events` sequence. Expected: `plan.clips == ()`, `plan.total_clips == 0` — no error (FR-012, Acceptance Scenario US1-4).

## Scenario 2 — Replay inclusion/exclusion (User Story 2)

1. Construct one event with `is_replay=True` and `include_replays=False` (default). Run detection. Expected: `plan.clips == ()` — no clip for that event (FR-004, Acceptance Scenario US2-1).
2. Re-run the same request with `include_replays=True`. Expected: one `PlannedClip` is produced, with `contains_replay=True` (FR-005, FR-011, Acceptance Scenario US2-2).
3. Construct a mix of replay and non-replay events with `include_replays=False`. Expected: `plan.clips` contains a clip only for each non-replay event; every non-replay event is represented (Acceptance Scenario US2-3).

## Scenario 3 — No duplicate or overlapping footage (User Story 3)

1. Construct two events whose computed clip windows overlap (e.g., timestamps 10s apart with an 8s/12s pre/post-roll). Run detection. Expected: one merged `PlannedClip` spanning both, `merged=True`, `event_count=2`, and its internal `ClipEvidence` records `MergeReason.OVERLAP` for the joining event (FR-006, Acceptance Scenario US3-1).
2. Construct two events whose windows don't overlap but are separated by a gap `<= merge_gap_seconds`. Expected: one merged clip, `MergeReason.GAP_THRESHOLD` (FR-006, Acceptance Scenario US3-2).
3. Construct two events separated by a gap `> merge_gap_seconds`. Expected: two separate `PlannedClip`s (Acceptance Scenario US3-3).
4. Construct three events whose windows chain together (each overlaps or gap-qualifies with the next, but the first and last don't directly relate). Expected: one merged clip spanning the full chain; the third event's `ClipEvidence.merge_reasons` records `MergeReason.CHAIN_MERGE` (FR-007, Acceptance Scenario US3-4).
5. Construct two events at the exact same `timestamp_seconds`. Expected: one `PlannedClip`, `event_count=2`, `source_event_ids` containing both `event_id`s in the FR-009 tie-break order (Acceptance Scenario US3-5).
6. Construct a mixed event set combining several independent merge groups (an overlap pair, a gap-threshold pair, a transitive chain) together with untouched singleton events, all in one request. Run to completion. Expected: for every pair of distinct output `PlannedClip`s, they neither overlap nor sit within `merge_gap_seconds` of each other — the plan-wide postcondition, not just each merge scenario checked in isolation (FR-008, SC-002).

## Scenario 4 — Traceability, determinism, and diagnostics

1. Run `generate_clips()` and inspect the internal `ClipEvidence` list. Expected: exactly one record per input event; every record either has a non-`null` `resulting_clip_id` or `excluded_due_to_replay=True`, never neither/both (FR-016, SC-008).
2. Run the same request twice. Expected: identical `plan.clips`, including identical `clip_id`, `source_event_ids` order, and `MergeReason` assignments (FR-014, SC-004, SC-007).
3. Call `generate_clips()` with `events=None` or `source_video_path=""`. Expected: `.run()` immediately raises `INVALID_INPUT`, with no event processed (FR-015).
4. Call `generate_clips()` with `merge_gap_seconds=-1`. Expected: `.run()` immediately raises `INVALID_CLIP_CONFIGURATION` (FR-015).
5. Construct an `events` sequence with zero events surviving Replay Filtering (all replay-flagged, `include_replays=False`). Run to completion. Expected: the run succeeds normally, and its diagnostics `output_summary` reports `average_clip_duration=0.0`, `final_clip_count=0` — never a crash (research.md Decision 6).
6. Construct a few hundred synthetic events (a representative full-match filtered set) and run `generate_clips()`, recording elapsed time. Expected: elapsed time is comfortably under the regression-tripwire ceiling (e.g., 5 seconds) — a negligible fraction of the platform's 2-minute `generate` budget (SC-006).

## Pass/fail

All four scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

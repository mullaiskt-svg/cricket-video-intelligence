# Tasks: Video Stitcher

**Input**: Design documents from `/specs/009-video-stitcher/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/video_stitcher_contract.md](./contracts/video_stitcher_contract.md), [quickstart.md](./quickstart.md)

**Tests**: Included — constitution Principle VII (Test-First Development) requires contract tests at module boundaries, tests written before implementation, and 100% coverage on critical paths (enforced by T045).

**Organization**: Tasks are grouped by user story (from spec.md) to enable independent implementation and testing of each story.

**Note on shared infrastructure**: This feature reuses `src/cvip/common/diagnostics.py`'s emitter and `pyproject.toml`'s existing pytest/coverage configuration (`[tool.coverage.run] source = ["src/cvip"]` already covers any new subpackage). Its input shape is Module 8's `ClipPlan`/`PlannedClip` (`cvip.clips.models`), consumed by structural shape, not a hard import requirement (research.md, mirroring Clip Generator's own `DetectedEventLike` precedent).

**Note on package layout**: Unlike `events/`/`clips/`, `src/cvip/stitcher/` was **not** pre-reserved as scaffolding in `specs/001-video-loader/plan.md`'s original layout (research.md Decision 1) — this feature creates it fresh, following the same short-name convention.

**Note on dependencies**: No new Python package dependency is introduced — FFmpeg/ffprobe are invoked directly via `subprocess`, matching Video Loader's own `ffprobe` precedent (`src/cvip/video/metadata.py`), not the dormant `ffmpeg-python` package already in `requirements.txt` (research.md Decision 2).

**Note on testing strategy (unique to this module)**: Unlike Event Detection and Clip Generator (fully testable against synthetic in-memory objects), this module's core job is invoking real FFmpeg processes and verifying real output — there is no way around real video fixtures for its integration/benchmark suite (research.md Decision 9). Its **unit** tests instead mock `stitcher/ffmpeg.py`'s wrapper functions to test orchestration logic (command construction, stage sequencing, failure routing) without spawning real subprocesses; its **integration/benchmark** tests use small real video fixtures generated by `tests/fixtures/video_stitcher/generate_fixtures.py` (T003), reusing `tests/fixtures/video_loader/`'s own ffmpeg-based fixture-generation approach.

**Note on validation placement**: As with Clip Generator, this feature implements the four Foundational-check failure reasons (`EMPTY_CLIP_PLAN`, `OUTPUT_ALREADY_EXISTS`, `MISSING_FFMPEG`, `SOURCE_VIDEO_UNAVAILABLE`) in the Foundational phase (T008) — none of them depend on the FFmpeg extraction/concatenation/output-validation logic, so implementing them early lets US1's contract test (T009) pass fully at that story's own checkpoint. The fifth failure reason, `STITCH_OPERATION_FAILED` (covering mid-run and Output Validation failures), is inherently US3's own concern and is implemented there.

## Notes

- [P] tasks touch different files and have no unmet dependencies
- [Story] label maps each task to its user story for traceability back to spec.md
- Commit after each task or logical group
- Stop at any checkpoint to validate a story independently before moving on
- **This module's unit/integration split is inverted relative to Modules 5/8**: because it exists to invoke real FFmpeg and verify real output, its integration suite (T012, T013, T018, T027, T028, T031, T033) needs real video fixtures, while its unit suite (T010, T011, T019, T020, T022-T026, T029, T030, T032) mocks `stitcher/ffmpeg.py`'s wrapper functions to test orchestration logic cheaply and deterministically. Neither layer alone would prove the feature works — the unit layer proves the *right commands* are constructed; the integration layer proves those commands *actually produce a valid file*.
- **FR-012/FR-013 (no OCR/replay/scene/DB access, no re-invoking earlier modules)**: satisfied by construction — `StitchRequest` (data-model.md) has no field capable of carrying a database handle, a video-analysis request, or a reference to any earlier module's entry point. Enforced by code review (T043), the same treatment as Event Detection's and Clip Generator's own analogous FRs.
- **FR-019 (no database writes)**: satisfied by construction — no code in `src/cvip/stitcher/` imports `sqlite3`, `cvip.db`, or any database-adjacent module; `StitchResult` and `StitchEvidence` (data-model.md) are plain in-memory dataclasses with no persistence method of their own. Database persistence of any kind (e.g., linking a generated highlight file back to the `events` rows it came from) remains the Pipeline Orchestrator's responsibility, not this module's. Enforced by code review (T043), the same treatment as FR-012/FR-013 above and as Event Detection's/Clip Generator's own analogous FRs.
- **The keyframe-snapping tolerance** (spec.md Assumptions, SC-003) means integration tests asserting output duration should use a small tolerance window (e.g., within one GOP length of the fixture's own encoding), not exact-second equality — the fixture-generation script (T003) should produce fixtures with a short, known GOP structure so this tolerance can be kept tight and the tests remain meaningful.
- **SC-001 (playback without corruption/errors)** is verified indirectly throughout — via Output Validation's own `ffprobe` check (T035) at runtime, and via the integration tests' own `ffprobe`-based inspection (T012, T018, T027) at test time — rather than via a literal video-player-in-the-loop test, consistent with how every prior module's "does this actually work correctly" claims are checked via structural/metadata inspection, not manual visual review.
- **SC-005 (well within the 2-minute `generate` budget)**: like Clip Generator's own SC-006, this module's actual cost is dominated by disk I/O and process-spawn overhead for a few dozen `ffmpeg` invocations, not codec work (stream-copy is CPU-light by construction) — T033's concrete threshold (e.g., <30 seconds) exists primarily as a regression tripwire (e.g., to catch an accidental fallback to re-encoding, or an accidental N+1 subprocess-spawn pattern), not because the 2-minute budget is actually tight.

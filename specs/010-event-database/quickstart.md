# Quickstart: Validating Event Database

This is a manual/automated validation guide for Event Database once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), and [contracts/event_database_contract.md](./contracts/event_database_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed — no new dependency is introduced by this feature (`sqlite3` is stdlib, research.md Technical Context).
- No upstream module needs to be implemented first — every batch this feature persists is built directly in Python as `ScoreboardReadingLike`/`ReplaySegmentLike`/`EventLike`-shaped records (research.md Decision 8 — structural, not hard, dependencies).
- **Unlike every prior module, this feature is tested against a real temporary SQLite file** (`tmp_path`), not synthetic in-memory-only fixtures — the whole point of this module is durability across a close/reopen cycle, which nothing purely in-memory can prove.

## Scenario 1 — Never waste the analysis budget twice (User Story 1)

1. Open a fresh database at a temp path. Call `check_analysis_status("abc123")`. Expected: `NOT_ANALYZED` (Acceptance Scenario US1-1).
2. Call `begin_analysis(MatchMetadata(file_hash="abc123", source_video_path="x.mp4"))`, then `complete_analysis()`. Call `check_analysis_status("abc123")` again. Expected: `COMPLETE` (Acceptance Scenario US1-2).
3. On a different `file_hash`, call `begin_analysis()` but not `complete_analysis()`. Expected: `check_analysis_status()` reports `IN_PROGRESS`, distinguishable from `COMPLETE` (Acceptance Scenario US1-3).
4. For the `COMPLETE` match from step 2, persist a small batch of events, then call `reset_for_forced_reanalysis("abc123")`. Expected: `query_events()` afterward returns `()`, and `check_analysis_status("abc123")` reports `IN_PROGRESS` (Acceptance Scenario US1-4).

## Scenario 2 — Every analysis result survives to generate highlights later (User Story 2)

1. `begin_analysis()`, then `persist_scoreboard_readings()` with a small batch, then `complete_analysis()`, then close the connection (`with` block exits). Open a **fresh** connection to the same path (simulating a later `cvip generate` process). Call `get_match_timeline()`. Expected: every reading is present, all fields intact, in timestamp order (Acceptance Scenario US2-1).
2. Same pattern with `persist_replays()`. Expected: every segment retrievable with all fields intact (Acceptance Scenario US2-2).
3. Same pattern with `persist_events()`. Expected: every event retrievable, all fields intact, `clip_start_seconds`/`clip_end_seconds` both `None` (Acceptance Scenario US2-3).
4. Call `update_clip_window(event_key, 10.0, 20.0)` for one persisted event. Expected: only that event's `clip_start_seconds`/`clip_end_seconds` change; every other column of that row, and every other row entirely, is untouched (Acceptance Scenario US2-4).

## Scenario 3 — Query and inspect what was found (User Story 3)

1. Persist events from multiple players. Query with `EventQueryFilter(player="Kohli")`. Expected: only Kohli's events returned, exact match (Acceptance Scenario US3-1).
2. Query with `event_types=("SIX",)`. Expected: only `SIX` events (Acceptance Scenario US3-2).
3. Query with `min_importance=80`. Expected: only events at or above that importance (Acceptance Scenario US3-3).
4. Query with `start_over=10, end_over=20`. Expected: only events whose `over_number` falls in `[10, 20]` (Acceptance Scenario US3-4).
5. Combine several filters. Expected: only events matching *all* of them (Acceptance Scenario US3-5).
6. Call `get_match_summary()`. Expected: duration/resolution/frame rate/codec, status, sample/event/replay counts, event counts by type, and average confidence by type, all accurate against what was persisted (Acceptance Scenario US3-6).
7. Call `get_match_timeline()`. Expected: every scoreboard reading and event included, `snake_case` field names (Acceptance Scenario US3-7).

## Scenario 4 — Fail clearly on corruption or misuse (User Story 4)

1. Write arbitrary non-SQLite bytes to a temp path. Call `open_database()` against it. Expected: `EventDatabaseError(CORRUPTED_DATABASE_FILE)`, before any table is queried (Acceptance Scenario US4-1).
2. Open a fresh database, close it, then manually set its `PRAGMA user_version` to an unexpected value. Reopen it. Expected: `EventDatabaseError(SCHEMA_VERSION_MISMATCH)` (Acceptance Scenario US4-2).
3. `begin_analysis()`, `complete_analysis()`, then call `persist_events()` again (no explicit reset). Expected: `EventDatabaseError(WRITE_AGAINST_COMPLETED_MATCH)` (Acceptance Scenario US4-3).

## Scenario 5 — Edge cases and diagnostics

1. Call `persist_events(())` (empty batch) on an `IN_PROGRESS` match. Expected: succeeds, zero rows inserted, no error (Edge Cases).
2. Query with a filter combination matching nothing. Expected: returns `()`, no error (Edge Cases).
3. Call `reset_for_forced_reanalysis()` for a `file_hash` with no prior `matches` row. Expected: treated as a fresh first-time analysis, no error (Edge Cases).
4. Persist a full-match-scale synthetic dataset (~12,600 scoreboard readings, a few hundred events, a few dozen replay segments) and time it. Expected: comfortably under a minute (SC-002, SC-005).
5. Inspect the diagnostics emitted across a full `begin` -> persist x3 -> `complete` sequence. Expected: one record per significant write operation (schema creation, each persist batch, each status transition), each including `schema_version=` (FR-020).

## Pass/fail

All five scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

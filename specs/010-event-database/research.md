# Phase 0 Research: Event Database

## Decision 1: A stateful `EventDatabase` object, not a single-`run()` Runner

**Decision**: `open_database(path: Path) -> EventDatabase` returns a context-manager object (`with open_database(path) as db:`) exposing several independent public methods (`check_analysis_status`, `begin_analysis`, `complete_analysis`, `fail_analysis`, `reset_for_forced_reanalysis`, `persist_scoreboard_readings`, `persist_replays`, `persist_events`, `update_clip_window`, `query_events`, `get_match_summary`, `get_match_timeline`) rather than the `detect_events(request)`/`.run() -> Result` shape every prior module (1-9) uses.

**Rationale**: Every prior module receives one complete, self-contained request and produces one complete, self-contained result in one call — that shape is what "single-pass analysis of an already-fully-known input" naturally produces. Event Database's own spec (Notes, checklist) is explicit that it is architecturally different: a *caller* (the Pipeline Orchestrator) drives a multi-step, multi-stage lifecycle over one open connection — check status, begin, persist after each of several upstream stages completes at different points in time, then complete or fail — and a *different* caller (`generate`/`inspect-db`/`export-timeline`) opens the same file later purely to read. Forcing this into a single `request in, result out` call would mean either (a) the caller assembles the *entire* match's data upfront and hands it over in one call, defeating the entire point of writing incrementally as each pipeline stage finishes (so a crash mid-`analyze` doesn't lose everything already computed), or (b) inventing an artificial multi-phase request/response protocol that's strictly more complex than just exposing the methods directly.

**Alternatives considered**: A single `run()` taking a tagged "operation" enum plus a payload (mimicking the single-entry-point shape while still being one call per operation) was considered; rejected as a needless layer of indirection over what is, in Python, already a clean method-per-operation object — it would not make testing, typing, or usage any clearer, and every other language-level convention here (context managers for lifecycle, typed methods for operations) already fits directly.

## Decision 2: `file_hash` is the identity for lifecycle operations; persistence/query operations take no match identifier at all

**Decision**: `check_analysis_status`, `begin_analysis`, `complete_analysis`, `fail_analysis`, and `reset_for_forced_reanalysis` all take `file_hash` explicitly. `persist_scoreboard_readings`, `persist_replays`, `persist_events`, `update_clip_window`, `query_events`, `get_match_summary`, and `get_match_timeline` take **no** match/file identifier parameter — they operate implicitly on "the" match the currently-open database file represents.

**Rationale**: Per `specs/technical_plan.md`'s Database Schema, one `.sqlite` file holds exactly one match's data (`match_id` = `file_hash[:12]` is the *filename*, not a foreign key inside the file) — `events`/`replays`/`scoreboard_readings` have no `match_id` column at all. `file_hash` genuinely needs to be a parameter for the lifecycle methods because it's the identity being checked or established *before* (or independent of) any `matches` row necessarily existing yet — `check_analysis_status` in particular must work against a freshly-created, still-empty database. Every other method runs strictly after `begin_analysis` has already established which match this file is for, so re-threading `file_hash` (or `match_id`) through every call would be pure, error-prone repetition of information the open connection already encodes.

**Alternatives considered**: Passing `match_id`/`file_hash` to every method uniformly (including persistence/query) for API consistency was considered; rejected as it would let a caller accidentally construct a request that names a *different* match than the one the open file actually represents, with no meaningful way to honor that mismatch — the one-file-one-match invariant makes the parameter both redundant and a source of a bug class that simply omitting it prevents entirely.

## Decision 3: Schema version stored via SQLite's own `PRAGMA user_version`

**Decision**: On creating a fresh database, `PRAGMA user_version = <SCHEMA_VERSION>` is set once, where `SCHEMA_VERSION` is a small integer constant owned by `db/schema.py` (starting at `1`). On opening an existing file, `PRAGMA user_version` is read back and compared; a mismatch is `SCHEMA_VERSION_MISMATCH` (FR-017).

**Rationale**: `user_version` is a dedicated 32-bit integer SQLite reserves in the database header specifically for this purpose — no extra table, no extra row, no risk of the version-tracking mechanism itself being affected by whatever migration prompted a version bump. Reading it is a zero-cost `PRAGMA` query that works even against a database whose *table* schema is otherwise unreadable, which matters for cleanly distinguishing "wrong version" (FR-017) from "not a valid SQLite file at all" (FR-016, Decision 4) — both need to be diagnosed before any table is queried.

**Alternatives considered**: A dedicated `schema_version` table (one row, one column) was considered, matching a pattern common in application-level migration frameworks; rejected as unnecessary — this module has no migration framework (schema changes across versions are out of MVP scope entirely, per the spec's Assumptions boundary), so `user_version`'s simplicity is strictly sufficient and avoids a table whose own creation would need to happen *before* the version check that's supposed to gate table creation.

## Decision 4: Corruption detection via `PRAGMA integrity_check` immediately after connecting

**Decision**: Immediately after `sqlite3.connect()` succeeds (which Python's `sqlite3` module allows even against a non-database file, since the file isn't actually read until a statement executes), `EventDatabase.__enter__` runs `PRAGMA integrity_check` and treats anything other than the single row `('ok',)` as `CORRUPTED_DATABASE_FILE` (FR-016), before any table-existence or `user_version` check runs.

**Rationale**: `sqlite3.connect()` on an arbitrary non-SQLite file (or a truncated/corrupted one) does not raise on connect — the first real read is what fails, and it fails with a generic `sqlite3.DatabaseError` whose message varies by corruption type. Running `integrity_check` explicitly, first, turns this into one deterministic, well-defined check with a single fail-fast reason, rather than letting corruption surface unpredictably as whatever the *first* real query downstream happens to be (which could otherwise be misreported as a schema-version mismatch or a missing-table error instead of what it actually is).

**Alternatives considered**: Relying on the first `CREATE TABLE IF NOT EXISTS` or `PRAGMA user_version` call to surface corruption naturally (via whatever `sqlite3.DatabaseError` it raises) was considered; rejected because it conflates two genuinely different failure reasons (FR-016 vs. FR-017) behind whichever check happens to run first, and because `CREATE TABLE IF NOT EXISTS` in particular can succeed or fail unpredictably against certain corrupted-but-partially-readable files depending on exactly which pages are damaged — an explicit `integrity_check` up front removes that ambiguity entirely.

## Decision 5: A cached in-memory match status, refreshed on every lifecycle transition, gates writes against a `COMPLETE` match

**Decision**: `EventDatabase` tracks `self._current_status: Optional[str]` (`None` until `begin_analysis`/`check_analysis_status` first establishes it), updated by every lifecycle method. `persist_scoreboard_readings`/`persist_replays`/`persist_events`/`update_clip_window` each check `self._current_status != "COMPLETE"` before writing (or bypass it entirely inside `reset_for_forced_reanalysis`'s own explicit-reset path) and raise `WRITE_AGAINST_COMPLETED_MATCH` (FR-018) otherwise.

**Rationale**: A cached flag avoids re-querying the `matches` table's `status` column on every single persistence call (which would run once per batch call, not once per row — still cheap either way, but the cache also means the *in-process* state machine (begin → persist* → complete/fail) is enforced the same way regardless of whether a caller re-reads status themselves in between) and keeps the enforcement point exactly where FR-018 describes it: at the moment of a write attempt, not as a separate pre-flight step every caller must remember to run.

**Alternatives considered**: Re-querying `SELECT status FROM matches` before every write was considered; rejected only for being a redundant round trip when the in-process cache already reflects the same information reliably within one open connection's lifetime (this module's own Assumptions rule out concurrent multi-process writers, so the cache can never go stale from another process's concurrent write).

## Decision 6: Query filters build one parameterized `WHERE` clause; `player`/`team` remain exact-match

**Decision**: `EventQueryFilter`'s fields (`player`, `team`, `event_types`, `min_importance`, `start_over`/`end_over`) are each translated to an `AND`-joined SQL condition only when supplied (`None`/empty = "no constraint from this field"), with every value passed as a bound parameter (`?` placeholders, `sqlite3`'s native parameterization) — never string-interpolated into the query text, even though this is a fully local, offline, single-user context with no untrusted network input.

**Rationale**: Directly implements FR-012's filter surface and `specs/cli.md`'s own documented exact-match-only semantics (no fuzzy matching) — `player`/`team` conditions are plain `= ?` equality, not `LIKE`. Parameterized binding is the standard, essentially free way to build this kind of dynamic query safely in `sqlite3` and avoids any accidental quoting bug from a player name containing an apostrophe (a real, likely case — e.g. "O'Brien" — not a hypothetical injection concern).

**Alternatives considered**: A small query-builder abstraction (a fluent/chainable filter object) was considered; rejected as unnecessary ceremony for five independently-optional, flatly-`AND`ed conditions — a single function building a `(where_clause, params)` pair directly from `EventQueryFilter`'s fields is simpler to read, test, and keep correct than a general-purpose builder this module has no other use for.

## Decision 7: `event_key` is not persisted — the schema's own `event_id` autoincrement primary key is the durable identity

**Decision**: `DetectedEvent.event_key` (Module 5's own deterministic, human-readable identifier — `specs/007-event-detection/spec.md` FR-025) is used only to correlate an in-memory `EventBatch` entry back to its source during persistence (e.g., logging/diagnostics); it is **not** written to the `events` table, which has no such column.

**Rationale**: `specs/technical_plan.md`'s Database Schema is authoritative and already finalized across every prior module's own spec (this plan's own Constitution Check notes design already treats it as settled, not open for negotiation here) — `events.event_id` (an autoincrement integer primary key SQLite assigns at insert time) is the schema's own durable row identity, and `event_key`'s entire purpose (per Module 5's own spec) was uniqueness *within one in-memory Event Detection Result*, before persistence — a concern that ends the moment a row has a real primary key.

**Alternatives considered**: Adding an `event_key TEXT` column to persist it anyway, for cross-referencing a stored row back to a specific Event Detection run's diagnostics, was considered; rejected as an unrequested schema change outside this spec's scope — `specs/technical_plan.md`'s schema is the single source of truth for column definitions, and none of FR-001 through FR-020 asks for this.

## Decision 8: Batch inputs are typed by structural shape, not hard-imported upstream dataclasses

**Decision**: `persist_scoreboard_readings`/`persist_replays`/`persist_events` accept sequences of objects matching a minimal structural `Protocol` (the exact fields each corresponding table column needs — e.g. for events: `event_type`, `timestamp_seconds`, `innings`, `over_number`, `ball_in_over`, `player`, `team`, `confidence`, `importance`, `milestone_value`, `is_replay`) rather than requiring the literal `cvip.events.models.DetectedEvent` / `cvip.video.scoreboard_ocr_models.ScoreboardSample` / `cvip.video.replay_detection_models.ReplaySegment` classes.

**Rationale**: Directly extends Clip Generator's own precedent (`specs/008-clip-generator/research.md` Decision 7) of depending on a field shape, not a concrete upstream type — keeps this module's own dependency surface to stdlib `sqlite3` only (this plan's Technical Context) and its own tests trivially buildable from minimal hand-built fixtures rather than needing every unrelated field of a full real `DetectedEvent`/`ScoreboardSample`/`ReplaySegment` populated just to exercise persistence.

**Alternatives considered**: Hard-importing all three upstream dataclasses was considered (this module already lives downstream of all three in the pipeline, so the import itself would be legal and not circular); rejected for the same reason Clip Generator rejected it — a structural dependency keeps this module testable and reasoned-about in isolation, and the field sets involved are small and stable enough that duplicating them as this module's own `Protocol`s costs little.

## Decision 9: Diagnostics reuse — no new infrastructure

**Decision**: `db/database.py` reuses `cvip.common.diagnostics` (`DiagnosticsTracker`/`ExecutionDiagnostics`/`emit_diagnostics`) exactly as every prior module does, emitting one diagnostics record per significant write operation (FR-020: database/schema creation, each single-pass status check, each bulk-insert batch, each status transition, each forced reset) — not one record for the entire connection's lifetime, since a single `EventDatabase` instance spans many independent operations across a whole `analyze` run, unlike every prior module's one-record-per-`.run()` precedent.

**Rationale**: FR-020 itself specifies "one diagnostics record per significant write operation," a deliberate departure from the platform's usual "exactly one record per module invocation" convention (Module 4a, Module 5, etc.) — because this module *is* invoked many times (once per method call) across one open connection's life, not once. Read-only queries are explicitly exempted (FR-020) since they can't fail in the ways this module's fail-fast taxonomy (FR-016 through FR-018) cares about once the connection itself is already known-good.

**Alternatives considered**: One diagnostics record per `EventDatabase` open/close lifecycle (aggregating every operation performed in between) was considered, matching the "one record per invocation" convention more literally; rejected because FR-020's own wording is explicit about per-operation granularity, and because a `FAILED` write partway through a long `analyze` run needs its own immediately-visible diagnostics record, not one buried inside a single end-of-lifetime summary that might never be reached if the process crashes before `__exit__` runs.

## Decision 10: `query_events()` exposes `event_key: str` (a stringified `event_id`), not a literal `event_id` field, to stay structurally compatible with Clip Generator's actual, already-implemented contract

**Decision**: `query_events()`'s returned row type (`QueriedEvent`, data-model.md) exposes `event_key: str` — `str(events.event_id)`, the SQLite auto-assigned integer primary key, stringified — alongside `timestamp_seconds` and `is_replay`, plus every other column `cvip inspect-db`/filtering needs.

**Rationale**: spec.md's FR-013 describes the required shape in prose as "an `event_id`/`timestamp_seconds`/`is_replay`-exposing shape," but Clip Generator's actual, already-merged, already-tested contract (`specs/008-clip-generator/research.md` Decision 7; verified directly against `src/cvip/clips/generator.py`'s own `getattr(event, "event_key", None)` validation) requires the attribute to be named exactly `event_key`, typed `str` — not `event_id`. FR-013's own stated intent is drop-in structural compatibility with Clip Generator's *existing* input contract (spec.md: "structurally compatible with Module 8's `ClipGenerationRequest.events` input... per Clip Generator's own structural contract") — honoring that intent means matching Clip Generator's real attribute name precisely, not FR-013's own imprecise paraphrase of it. Clip Generator is an already-merged, tested module (PR #9); this module conforms to its real contract rather than the reverse.

**Alternatives considered**: Exposing a literal `event_id: int` field (matching FR-013's prose and the schema's own column name) and requiring the caller (the Pipeline Orchestrator, assembling `ClipGenerationRequest`) to adapt it to `event_key: str` itself was considered; rejected as pushing an avoidable adaptation step onto every caller of `query_events()` for no benefit — this module can trivially produce the exact shape Clip Generator already expects, so it does.

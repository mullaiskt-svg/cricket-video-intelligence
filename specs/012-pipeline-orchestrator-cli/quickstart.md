# Quickstart: Validating Pipeline Orchestrator and CLI

This is a manual/automated validation guide for this feature once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), [contracts/orchestrator_contract.md](./contracts/orchestrator_contract.md), and [contracts/cli_contract.md](./contracts/cli_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed — no new dependency beyond stdlib `argparse` and the already-present `PyYAML` (research.md).
- Every module this feature calls (Modules 1-10) is already implemented and merged — no upstream work needed first.
- **Almost all scenarios below use every pipeline module mocked** (`mocker.patch`), per research.md Decision 5 — this feature's own job is sequencing/translation, not detection, so its test suite proves wiring correctness, not detection accuracy. The one exception (Scenario 6) uses a real, tiny (5-second) video fixture already present in the repo (`tests/fixtures/video_loader/valid_short.mp4`).

## Scenario 1 — Analyze a match end to end (User Story 1)

1. Mock every pipeline module (`load_video`, `detect_scenes`, `detect_replays`, `extract_scoreboard`, `smooth_timeline`, `detect_events`) to return known-good synthetic results, and mock `EventDatabase` to a real `tmp_path`-backed instance (Event Database's own test pattern, not mocked — this is the one dependency worth exercising for real). Call `orchestrator.analyze(request)`. Expected: every mock is called exactly once, in order; the database ends with a `COMPLETE` match row, persisted readings/replays/events matching what each mocked stage returned (FR-001, FR-004, FR-005, Acceptance Scenario US1-1).
2. Seed the database with an existing `COMPLETE` match row for the same `file_hash` the mocked Video Loader will report. Call `analyze()` without `force`. Expected: `OrchestratorError(ALREADY_ANALYZED)` raised before `detect_scenes` (or any stage after Video Loader) is ever called (FR-002, Acceptance Scenario US1-2).
3. Same seeded database, call `analyze()` with `force=True`. Expected: prior data is cleared (`reset_for_forced_reanalysis` called), and every stage runs fresh (FR-003, Acceptance Scenario US1-3).
4. Mock `detect_replays` to raise `ReplayDetectionError`. Call `analyze()`. Expected: `detect_scenes` was called, `extract_scoreboard`/`smooth_timeline`/`detect_events` were never called, the match row ends `FAILED`, and `OrchestratorError` is raised with the correctly-translated reason (FR-005, Acceptance Scenario US1-4).
5. Seed an `IN_PROGRESS` (not `COMPLETE`) match row for the target `file_hash`. Call `analyze()` without `force`. Expected: `OrchestratorError(ALREADY_ANALYZED)`, identical to Step 2 (FR-002, Acceptance Scenario US1-5, Assumptions — no partial resume attempted).

## Scenario 2 — Generate highlights from an already-analyzed match (User Story 2)

1. Seed a database with several persisted events. Mock `generate_clips`/`stitch_video`. Call `orchestrator.generate(request)` with `template="match"` and no filters. Expected: `query_events()` was called with an all-`None` filter, its result was passed to `generate_clips` unmodified, and `Video Loader`/`Scene Detection`/`Replay Detection`/`Scoreboard OCR`/`OCR Timeline Smoother`/`Event Detection` were never imported or called anywhere in this call's graph (FR-006, Acceptance Scenario US2-1).
2. Same setup, call `generate()` with `min_importance`/`start_over`/`end_over`/`event_types` set. Expected: `query_events()` was called with an `EventQueryFilter` matching those exact values (FR-006, Acceptance Scenario US2-2).
3. Call `generate()` with `template="player"`. Expected: `OrchestratorError(INVALID_ARGUMENTS)` with a "not yet implemented — planned for V1.5" detail message, and no database is ever opened (FR-007, Acceptance Scenario US2-3).
4. Call `generate()` with a `match_id` whose database file doesn't exist. Expected: `OrchestratorError(MISSING_INPUT_FILE)` (FR-008, Acceptance Scenario US2-4).

## Scenario 3 — Inspect and export (User Stories 3, 4)

1. Seed a database with known match metadata, readings, and events. Call `orchestrator.inspect_db(db_path)`. Expected: the returned `MatchSummary`'s every field matches exactly what was seeded (FR-010, Acceptance Scenario US3-1).
2. Call `inspect_db()` against a nonexistent path. Expected: `OrchestratorError(MISSING_INPUT_FILE)` (Acceptance Scenario US3-2).
3. Call `orchestrator.export_timeline(match_id, db_path)` against the same seeded database. Expected: the returned `MatchTimelineExport` contains every seeded reading and event, `snake_case`-keyed (FR-009, Acceptance Scenario US4-1). Separately, confirm `cli.py`'s own CSV serialization of the same data covers the same events (Acceptance Scenario US4-2).

## Scenario 4 — Environment validation (User Story 5)

1. With every dependency genuinely present on the test machine, call `orchestrator.run_doctor_checks()`. Expected: every `DependencyCheckResult.ok` is `True` (Acceptance Scenario US5-1).
2. Mock `shutil.which("ffmpeg")` to return `None`. Call `run_doctor_checks()`. Expected: the FFmpeg check's `ok` is `False` with a specific `detail`, while every other check still ran and reports its own independent result (Acceptance Scenario US5-2).

## Scenario 5 — Exit code coverage (SC-004)

For each of the nine non-zero `OrchestratorFailureReason` values, construct the specific condition that triggers it (per research.md Decision 7's mapping table) and confirm `cli.py`'s `main()` calls `sys.exit()` with the exact matching code — one dedicated test per code, not a single generic assertion.

## Scenario 6 — Real, unmocked smoke test (research.md Decision 5)

Run `orchestrator.analyze()` for real (no mocks at all) against `tests/fixtures/video_loader/valid_short.mp4`, with a real `tmp_path`-backed Event Database and a real, minimal config. Expected: the run completes without raising, ends with a `COMPLETE` match row (even if `event_count == 0`, since this fixture has no real scoreboard content — this test proves the wiring executes, not that it detects anything). This is this feature's only test allowed to take more than a couple of seconds, and lives in `tests/benchmark/`, deselected by default.

## Pass/fail

All six scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.

All scenarios pass. No deviations found. Full regression suite (577 tests across all eleven features, now including `src/cvip/{orchestrator,orchestrator_models,orchestrator_errors,cli}.py`) passes, and `pytest --cov=src/cvip/orchestrator.py --cov=src/cvip/orchestrator_models.py --cov=src/cvip/orchestrator_errors.py --cov=src/cvip/cli.py --cov-fail-under=100` reports 100% coverage across all four new files.

Two real, confirmed implementation bugs were found and fixed during test-writing itself, not left latent: (1) `analyze()`'s generic exception handler would have let a raw `EventDatabaseError` from a `persist_*()` call escape unwrapped past `cli.py`'s `except OrchestratorError` handler, crashing instead of exiting cleanly with code 7 -- fixed by adding an explicit `except EventDatabaseError` translation. (2) `cli.py`'s `main()` initially caught only `OrchestratorError`, leaving GENERAL_FAILURE's own documented "any unanticipated exception" case unenforced -- fixed by adding a catch-all safety net.

# Phase 0 Research: Pipeline Orchestrator and CLI

## Decision 1: `analyze()`/`generate()` are plain functions, not context-manager Runners

**Decision**: `orchestrator.py` exposes `analyze(request: AnalyzeRequest) -> AnalysisRun` and `generate(request: GenerateRequest) -> GenerateResult` as plain functions — not the `with X(request) as runner: runner.run()` shape every detection/transformation module (Modules 2-9) uses.

**Rationale**: The Runner-context-manager pattern exists on every prior module specifically to support mid-run cancellation (`.cancel()`) and post-run internal-evidence inspection (`.evidence`) — neither applies here. `analyze()`/`generate()` are themselves the *composition* of nine already-Runner-shaped modules, each of which already owns its own cancellation/evidence/diagnostics; the Orchestrator's only job on top of that is sequencing, translation, and persistence. Event Database (Module 10) already established the platform's precedent that a module's shape should follow its actual need, explicitly documented, rather than cargo-culting the Runner pattern everywhere (`specs/010-event-database/research.md` Decision 1) — this is the same judgment applied here, in the opposite direction (a *simpler* shape than the default, not a *more complex* one).

**Alternatives considered**: A `PipelineOrchestrator` class wrapping `analyze()`/`generate()` as methods, mainly for symmetry with Event Database's own multi-method object, was considered; rejected because Event Database's multi-method shape exists specifically to hold one open, stateful SQLite connection across many calls — `analyze()`/`generate()` have no comparable shared, stateful resource of their own to hold open across multiple calls (each opens and closes its own `EventDatabase` connection internally, within one call).

## Decision 2: Frame Extraction (Module 1a) has no Orchestrator-level call site

**Decision**: `analyze()`'s explicit sequence is Video Loader → Scene Detection → Replay Detection → Scoreboard OCR → OCR Timeline Smoother → Event Detection — six calls, not seven. Frame Extraction is never called directly by the Orchestrator.

**Rationale**: Confirmed directly against the real implementation (`scene_detection.py`, `replay_detection.py`, `scoreboard_ocr.py` each import and call `cvip.video.frame_extraction.extract_frames()` internally, at their own required sampling rate/mode). Module 1a is a shared *library* three other modules already depend on, not a pipeline *stage* with its own input/output contract at the Orchestrator's level of sequencing. `specs/technical_plan.md`'s own "1→1a→2→3→4→4a→5" phrasing describes the conceptual data-flow, not a literal call sequence — this decision reconciles that phrasing with the modules' actual, already-built calling convention rather than introducing a redundant, disruptive fourth call site.

**Alternatives considered**: Having the Orchestrator extract frames once and pass the resulting frame sequence into Scene Detection/Replay Detection/Scoreboard OCR was considered (a literal reading of "Frame Extraction is a shared service"); rejected because it would require changing three already-implemented, already-tested modules' own request contracts (each currently takes a `LoadResult` and extracts its own frames at its own sampling rate/mode internally) — out of scope for a feature whose entire premise is composing already-built modules unchanged, not modifying them.

## Decision 3: The single-pass check runs immediately after Video Loader, before any expensive stage

**Decision**: `analyze()`'s sequence is: run Video Loader (cheap — `cv2.VideoCapture` metadata probe plus a *sampled*, not full-file, hash digest, per `hashing.py`'s own research note) → open the Event Database → check the resulting `file_hash` against existing match records → gate here (FR-002) → only then run Scene Detection onward.

**Rationale**: FR-002 requires the single-pass check to happen "before any pipeline stage runs... without decoding any frame," but `file_hash` is Video Loader's own output (FR-014 in its own spec) — it cannot be known before Video Loader runs at all. The resolution is that Video Loader itself does not decode frames in the sense FR-002 cares about (no `Frame Extraction`/OpenCV per-frame loop) — it is a fast metadata probe. Running it first, then gating immediately afterward and before Scene Detection (the first stage that actually calls into Frame Extraction), satisfies FR-002's real intent — no expensive per-frame work happens for an already-analyzed file — without requiring a second, redundant hash computation the Orchestrator would otherwise have to invent.

**Alternatives considered**: Computing `file_hash` independently inside the Orchestrator before calling Video Loader at all was considered, to gate with zero Video Loader involvement; rejected as needless duplication of `hashing.compute_file_hash()`'s own already-correct, already-tested logic, and because Video Loader's own metadata (duration/resolution/frame_rate/codec) is needed for the `matches` row (Event Database's `MatchMetadata`) regardless, so Video Loader has to run early either way.

## Decision 4: Config-to-request translation happens inline, one stage at a time — no upfront "build everything" step

**Decision**: `analyze()` loads `config/default.yaml` once at the very start (via `PyYAML`), but builds each stage's own `Request` dataclass immediately before calling that stage, not all at once upfront.

**Rationale**: Several downstream requests structurally require an upstream *result*, not just config values — `ReplayDetectionRequest` needs `SceneDetectionResult`, `EventDetectionRequest` needs the OCR Timeline Smoother's cleaned timeline plus the raw OCR result plus the replay result. A single upfront "build every request" function cannot exist without either (a) running every stage first anyway (defeating the point of an upfront step), or (b) representing not-yet-available results as `None`/placeholders — a worse, more error-prone shape than simply building each request at the point it's actually needed, in the same sequential pass that calls each stage.

**Alternatives considered**: A `PipelineConfig` dataclass parsed once and threaded through every stage call as a single bundle was considered, for a cleaner call signature; rejected as unnecessary indirection for six call sites, each of which only needs a handful of that config's own fields — passing the raw parsed config dict (or a thin, already-validated `OrchestratorConfig` wrapper, data-model.md) directly is simpler and avoids a bundle type with no other use.

## Decision 5: A deliberately three-tiered test strategy — mocked sequencing, mocked CLI, and exactly one real smoke test

**Decision**: (1) `orchestrator.py`'s own sequencing/translation/gating logic is unit-tested with every pipeline module's entry point mocked (`mocker.patch("cvip.video.scene_detection.detect_scenes", ...)` etc.) — verifying call order, config-to-request field mapping, single-pass gating, and fail-fast-on-first-error, without ever running real OpenCV/Tesseract/FFmpeg work. (2) `cli.py`'s argument parsing, help text, and exit-code translation are unit-tested with `cvip.orchestrator.analyze`/`generate` themselves mocked. (3) Exactly one real, slow, full-pipeline integration test (`tests/benchmark/test_orchestrator_e2e_smoke.py`, deselected by default like every prior benchmark test) runs `analyze()` for real, end-to-end, against `tests/fixtures/video_loader/valid_short.mp4` (a real 5-second fixture with no actual cricket scoreboard content).

**Rationale**: This feature's entire premise is that Modules 1-10 are already independently correct and independently tested — re-proving their own internal correctness here would be pure duplication. What this feature actually needs proven is: are they wired together correctly (right call order, right field translations, right persistence timing, right failure propagation)? Mocking every module call answers exactly that question, fast, deterministically, and without needing a real multi-hour match video in the test suite. The one real smoke test exists because mocks can drift from the real contracts they stand in for (a mock that accepts the wrong keyword argument would still "pass") — running the genuine, unmocked sequence against a tiny real file (not a real match, since a real match's OCR/scene-detection stages measured 90-120 minutes each in this project's own real-data work, entirely unsuitable for a test suite) proves the actual wiring compiles and executes without raising, independent of what it detects. Detection *accuracy* on a real match remains each underlying module's own already-measured, already-documented concern (`specs/005-scoreboard-ocr/spec.md`, `specs/007-event-detection/spec.md`'s own amendments) — not something this feature's test suite re-litigates.

**Alternatives considered**: A full real-match integration test (using `tests/fixtures/video_loader/First8Overs.mp4`, a real ~40-minute broadcast already present in the repo) was considered, for a genuinely meaningful accuracy check at the orchestration level; rejected as wildly disproportionate to what this feature needs to prove (wiring, not accuracy) and would make the test suite's already-existing benchmark tier (currently seconds-to-low-minutes across every prior module) balloon to well over an hour for one single test.

## Decision 6: Native-dependency preflight check shared between `analyze()` and `cvip doctor`

**Decision**: A single internal helper, `_check_native_dependencies() -> List[DependencyCheckResult]` (checking `shutil.which("ffmpeg")` and `shutil.which("tesseract")`), is called both by `cvip doctor` (reporting every check's own result) and by `analyze()` as a preflight step immediately after the single-pass gate passes, before Scene Detection begins — failing fast with exit code 5 (missing native dependency) if either is absent, rather than letting the failure surface deep inside a run (e.g. Scoreboard OCR failing via an unwrapped `pytesseract.TesseractNotFoundError`, or Video Stitcher's own already-defined `MISSING_FFMPEG` reason only surfacing after `analyze` has already spent 40 minutes on everything before it).

**Rationale**: `ScoreboardOcrFailureReason` (the module Tesseract actually runs inside) has no "Tesseract missing" value of its own — a missing Tesseract binary would otherwise propagate as a raw, unwrapped `pytesseract` exception, uncaught by this feature's own exit-code translation (FR-012) unless specifically anticipated. Checking upfront, once, before any expensive stage runs, is both cheap and exactly what `constitution` Principle VI ("fail fast... never fall back to a silent default") asks for — finding out FFmpeg is missing 39 minutes into a 40-minute `analyze` run (right as Video Stitcher would need it, if `generate` were being tested this way) is a far worse experience than finding out in the first second.

**Alternatives considered**: Only checking at the point each dependency is actually used (Tesseract at Scoreboard OCR, FFmpeg at Video Stitcher) was considered, avoiding any new preflight logic; rejected because `analyze()` never calls Video Stitcher at all (that's `generate()`'s job) — so a missing-FFmpeg condition would never be caught during `analyze` under this alternative, only surfacing much later during a separate `generate` invocation, which is a worse diagnostic experience for a condition that was true and checkable from the very start.

## Decision 7: Exit-code translation happens in `orchestrator.py`, at the exact point each stage's typed exception is caught — not a generic lookup table in `cli.py`

**Decision**: Every pipeline-module exception type this feature can encounter (`FailureReason` from Video Loader, `SceneDetectionFailureReason`, `ReplayDetectionFailureReason`, `ScoreboardOcrFailureReason`, `OCRTimelineSmootherFailureReason`, `EventDetectionFailureReason`, `ClipGenerationFailureReason`, `VideoStitchingFailureReason`, `EventDatabaseFailureReason`) is caught at its own call site inside `orchestrator.py`, immediately wrapped into this feature's own `OrchestratorError(reason: OrchestratorFailureReason, exit_code: int, detail: str)` (`orchestrator_errors.py`), and re-raised. `cli.py` catches only `OrchestratorError` at its own top level and calls `sys.exit(error.exit_code)` — it contains no per-module-reason knowledge of its own (FR-015).

**Rationale**: The mapping from "which specific reason, from which specific module, failed" to "which of the ten exit codes applies" genuinely depends on *which stage* was running when the failure happened — the same underlying condition can map differently depending on context (e.g. `EventDatabaseError(CORRUPTED_DATABASE_FILE)` is exit code 7 regardless of which stage triggered a write, but a missing-Tesseract-style condition is exit code 5 specifically because it's a *dependency* problem, not a database or OCR-logic problem, even though it surfaces from inside the OCR stage). `orchestrator.py` already has this context naturally, at the point it made each call; a separate, generic `(module, reason) -> exit_code` lookup table living in `cli.py` would have to reconstruct that same context from the exception alone, and would violate FR-015's requirement that `cli.py` contain zero pipeline-sequencing/reason-specific knowledge.

**Concrete mapping** (`orchestrator_errors.py`'s `OrchestratorFailureReason` enum, one member per exit code 1 through 9):

| Exit code | `OrchestratorFailureReason` | Populated from |
|---|---|---|
| 1 | `GENERAL_FAILURE` | Any unanticipated exception not otherwise mapped below (a deliberate catch-all, never silently swallowed — still logged and re-raised as this reason) |
| 2 | `INVALID_ARGUMENTS` | argparse-level errors (`cli.py`, before `orchestrator.py` is ever called); every module's own `INVALID_*_CONFIGURATION`/structural `INVALID_INPUT` reason |
| 3 | `MISSING_INPUT_FILE` | Video Loader's `FILE_NOT_FOUND`; a `generate`/`inspect-db`/`export-timeline` `match_id`/db path with no corresponding file |
| 4 | `UNSUPPORTED_VIDEO_FORMAT` | Video Loader's `UNSUPPORTED_FORMAT` |
| 5 | `MISSING_NATIVE_DEPENDENCY` | Decision 6's preflight check; Video Stitcher's own `MISSING_FFMPEG` |
| 6 | `OCR_FAILURE` | `ScoreboardOcrFailureReason`'s run-level reasons (`SOURCE_UNAVAILABLE_MID_RUN`, `DECODE_FAILURE_MID_RUN`, `SOURCE_NOT_VALIDATED`) once past the Decision 6 preflight (i.e., Tesseract *is* present, but something else in the OCR stage failed) |
| 7 | `DATABASE_FAILURE` | Every `EventDatabaseFailureReason` value |
| 8 | `EXPORT_FAILURE` | `VideoStitchingFailureReason`'s non-dependency reasons (`EMPTY_CLIP_PLAN`, `OUTPUT_ALREADY_EXISTS`, `SOURCE_VIDEO_UNAVAILABLE`, `STITCH_OPERATION_FAILED`) |
| 9 | `ALREADY_ANALYZED` | The single-pass gate itself (Decision 3) — a `COMPLETE` or `IN_PROGRESS` match record found without `--force` |

`SceneDetectionFailureReason`'s and `ReplayDetectionFailureReason`'s own `SOURCE_UNAVAILABLE_MID_RUN`/`DECODE_FAILURE_MID_RUN` reasons, and `ClipGenerationFailureReason`'s `INVALID_INPUT` (a structural shape mismatch from the Event Database query, which should never actually happen given Decision 10 of Event Database's own research.md, but is defensively handled) map to `GENERAL_FAILURE` (exit 1) — genuine mid-run I/O failures during video decode, not cleanly any of the other nine specific categories.

**Alternatives considered**: A flat `Dict[Type[Exception], int]` global mapping table, keyed purely by exception class, was considered; rejected because several exception *types* (e.g. `ScoreboardOcrError`) map to *different* exit codes depending on the specific `.reason` value carried inside them (Decision 6's Tesseract-missing case vs. a genuine mid-run OCR failure both raise conceptually similar errors from the same module) — a table keyed on type alone cannot express that distinction; explicit per-call-site handling in `orchestrator.py` can.

## Decision 8: `AnalyzeRequest`/`GenerateRequest` are built by `cli.py` from parsed `argparse` output; `orchestrator.py` never reads `sys.argv`, `config/default.yaml`'s raw dict, or any CLI flag by name

**Decision**: `cli.py` parses arguments, loads and validates `config/default.yaml` into a plain dict, and constructs a fully-formed `AnalyzeRequest`/`GenerateRequest` (data-model.md) before calling `cvip.orchestrator.analyze()`/`generate()`. `orchestrator.py` never imports `argparse`, `sys.argv`, or `yaml` itself.

**Rationale**: Directly implements FR-015 (`cli.py` does argument parsing and delegation only; `orchestrator.py` does sequencing only) and mirrors every prior module's own "config-derived values are caller-supplied, not read from the file directly by the module" precedent (Event Detection's `ranking`/`team_milestone_interval`, Clip Generator's `pre_roll_seconds` etc.) — applied here one layer up, since `orchestrator.py` is itself now the "module" and `cli.py` is its caller. This also makes `orchestrator.py` fully testable by constructing `AnalyzeRequest`/`GenerateRequest` directly in Python, exactly like every other module's own test suite, without needing to invoke `argparse` or write a real YAML file to disk for a unit test.

**Alternatives considered**: Having `orchestrator.py` accept a `config_path: str` and load YAML itself was considered, for a shorter `cli.py`; rejected as it would blur the two-layer separation FR-015 explicitly requires, and would make `orchestrator.py`'s own unit tests need a real file on disk (or extensive `mocker.patch("builtins.open", ...)` ceremony) just to exercise sequencing logic that has nothing to do with file I/O.

**Implementation correction**: `data-model.md`'s original draft of `GenerateRequest` typed its filter field as a pre-built `cvip.db.models.EventQueryFilter`, which would have forced `cli.py` to import `cvip.db` directly to construct one — a direct violation of this very decision and of FR-015. Fixed during implementation: `GenerateRequest` carries the filter as plain primitives (`player`, `team`, `event_types`, `min_importance`, `start_over`, `end_over`); `orchestrator.generate()` builds the real `EventQueryFilter` internally, since it already imports `cvip.db` regardless.

## Decision 9: `orchestrator.py` reconstructs `scoreboard_readings.innings` itself, since no upstream module produces it

**Decision**: Neither `ScoreboardSample` (Scoreboard OCR's own output) nor `CleanedScoreboardSample` (the OCR Timeline Smoother's) carries an `innings` field, but `specs/technical_plan.md`'s schema requires one on every `scoreboard_readings` row, and Event Database's own `ScoreboardReadingLike` protocol (`specs/010-event-database/data-model.md`, written anticipating exactly this gap) requires it too. `analyze()` computes it itself, immediately before calling `persist_scoreboard_readings()`, using the identical "both `runs` and `wickets` decreased relative to the last reading with both non-null" heuristic Scoreboard OCR's own validation and Event Detection's own FR-010 already establish as this platform's one and only innings-transition signal — applied here as a simple forward scan over the raw samples (starting at innings `1`, incrementing on each detected transition), wrapping each `ScoreboardSample` in a small adapter object exposing the computed `innings` alongside every other field unchanged.

**Rationale**: This is not new detection logic — it is the same, already-established, already-validated heuristic, applied at a different point (a full timeline scan for persistence) than where it already runs today (Scoreboard OCR's own single-prior-reading validation check, Event Detection's own running counter). Duplicating a five-line, already-proven comparison is far simpler and lower-risk than modifying any already-merged, already-tested module's public contract to additionally expose per-sample innings — which this feature's own scope (composing existing modules, not changing them) rules out.

**Alternatives considered**: Persisting `innings=1` unconditionally for every reading (deferring true multi-innings tracking as a documented limitation, the same way `team` is left `NULL` throughout this platform for lack of a data source) was considered; rejected because, unlike `team`, a derivation *does* exist and is already established elsewhere in the codebase — choosing not to use it would make `scoreboard_readings.innings` actively wrong (not merely absent) for every second-innings reading in a real match, which is worse than the honest `NULL` `team` precedent it would otherwise resemble.

# Quickstart: Validating the Structured Match Metadata Validation Layer

This is a manual/automated validation guide for this feature once implemented per [plan.md](./plan.md), [data-model.md](./data-model.md), [contracts/metadata_pipeline_contract.md](./contracts/metadata_pipeline_contract.md), and [contracts/orchestrator_validate_contract.md](./contracts/orchestrator_validate_contract.md). It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps.

## Prerequisites

- Python 3.11+ environment with project dependencies installed — no new dependency (research.md Technical Context).
- Event Database (Module 10) upgraded to schema version 2 (data-model.md) — a fresh `cvip analyze` run against any video produces a v2 database; an old v1 database needs `cvip analyze --force` before this feature can write to it.
- Most scenarios below use a small, hand-built `tmp_path`-backed Event Database seeded directly with known scoreboard readings/events, plus a small hand-built metadata JSON fixture — this feature's own job is alignment/reporting/recovery logic, not detection, so its test suite proves that logic correctness, not video-analysis accuracy. The one exception (Scenario 5) uses this project's own real, already-validated dataset.

## Scenario 1 — Accuracy reporting (User Story 1)

1. Seed a database with a `COMPLETE` match, several `scoreboard_readings`, and several `events`. Build a metadata fixture whose events partially overlap the seeded `events` (some matching exactly, some referencing a position with no nearby reading at all, some referencing a position with a nearby reading but no matching detected event). Call `cvip validate <match> --metadata <file>` with no other flags. Expected: the printed/written `AccuracyReport` shows correct true-positive/false-negative/false-positive counts and recall/precision per event type (FR-006, Acceptance Scenario US1-1).
2. In the same report, confirm the no-signal miss and the signal-but-missed miss are each listed under their own distinct outcome, not merged into one "missed" bucket (FR-007, Acceptance Scenario US1-2).
3. Build a metadata fixture referencing an over number beyond the seeded match's own known range. Call `cvip validate`. Expected: a specific, clear error (`POSITION_OUT_OF_RANGE` → exit code 2), not a report that silently ignores the bad entry (FR-015, Acceptance Scenario US1-3).
4. Seed a database whose match status is `IN_PROGRESS` (not `COMPLETE`). Call `cvip validate`. Expected: refused with a clear error (`MATCH_NOT_COMPLETE` → exit code 2) before any metadata file is even read (FR-008, Edge Cases).
5. Call `cvip validate` twice against the identical seeded database and metadata file. Expected: byte-identical `AccuracyReport` both times (FR-018) — this is the determinism contract test.

## Scenario 2 — Event recovery (User Story 2)

1. Using Scenario 1's fixture, call `cvip validate <match> --metadata <file> --recover`. Expected: exactly one new `events` row is created for the signal-but-missed event, with `source='METADATA'` and a `timestamp_seconds` matching the nearby reading found in Scenario 1 (FR-010, FR-011, Acceptance Scenario US2-1). A matching `metadata_operations` row (`operation_type='RECOVERY'`) exists, satisfying FR-017's audit requirement — queryable directly, no external log needed.
2. Confirm the no-signal miss from Scenario 1 is reported as unrecoverable and no row is created for it, even with `--recover` supplied (FR-010's own precondition, Acceptance Scenario US2-2).
3. Confirm every pre-existing `events` row, and the match's own `status`, are byte-identical before and after this recovery run (FR-013, Acceptance Scenario US2-3).
4. Run `--recover` a second time against the same database and metadata file. Expected: no new `events` row is created the second time (the pre-write `metadata_operations` check, research.md Decision 6), and the total event count is unchanged from after Step 1 (FR-012, Acceptance Scenario US2-4).

## Scenario 3 — Wicket enrichment (User Story 3)

1. Seed a `WICKET` event whose corresponding metadata description states a fielder caught the batter (e.g. `"c Dileep KP b Sai Kiran"` — real phrasing from this project's own commentary data). Call `cvip validate <match> --metadata <file> --enrich`. Expected: the event's `dismissal_type` becomes `CAUGHT` and `fielder` becomes `"Dileep KP"`, with an `ENRICHMENT` row in `metadata_operations` (FR-014, Acceptance Scenario US3-1).
2. Seed a `WICKET` event whose metadata description doesn't match any recognized phrasing (research.md Decision 9). Call `--enrich`. Expected: `dismissal_type`/`fielder` remain `NULL`, and no `metadata_operations` row is created for that event, since nothing was actually changed (FR-014, Acceptance Scenario US3-2).
3. Confirm the enriched event's `timestamp_seconds`, `confidence`, and `event_type` are unchanged from before enrichment.

## Scenario 4 — CLI surface and read-only-by-default guarantee (research.md Decision 8)

1. Call `cvip validate <match> --metadata <file>` with neither `--recover` nor `--enrich`. With the Event Database mocked, assert no write method (only `check_analysis_status`, read-only `scoreboard_readings`/`events` access) is ever called (FR-003's structural enforcement).
2. Confirm `cli.py`'s existing static-import contract test (`tests/contract/test_cli_contract.py`) still passes unmodified, extended to also assert `cli.py` never imports `cvip.metadata` directly, only `cvip.orchestrator`.
3. Confirm `analyze`/`generate`/`export-timeline`/`inspect-db`/`doctor`'s own existing test suites all still pass unmodified — proof this feature changed nothing about them.

## Scenario 5 — Real dataset reproduction (SC-002)

Run `cvip validate` against a real, already-analyzed run of this project's own Wild Wanderers vs Phoenix Firehawks match, using `ground_truth_v2`'s real commentary files converted through `build_ground_truth.py`'s same classification logic (now the production `BallByBallJsonProvider`). Expected: the reproduced recall figure matches the already-established 14.0% (57 ground-truth events, prior ad hoc investigation) within a small tolerance — this is the one test in the suite allowed to depend on real match data, mirroring the Orchestrator feature's own one-real-smoke-test precedent.

## Pass/fail

All five scenarios must pass exactly as described for this feature to be considered validated end-to-end. Any deviation should be filed against the relevant functional requirement or success criterion in [spec.md](./spec.md) rather than patched ad hoc.
